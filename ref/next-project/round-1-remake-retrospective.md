## 2. 项目的真实演进

### A. 先建立原版基线，而不是先选 Web 架构

**时间：2026-07-13 至 07-16**

项目从原物、逆向结果和原版 GDD 起步，先回答资源在哪里、规则如何运行、哪些结论有证据。
这一阶段形成了后续最重要的方向：原版事实不由 Web 实现反推，原始资源不直接成为浏览器运行时
依赖。

有效做法：

- 保留原始字节、偏移、记录号和哈希；
- 把解析结果逐步转成机器 JSON；
- 将取证结论与复刻产品决定分开；
- 对未知行为保留未知，不用“看起来合理”的实现填空。

早期不足：项目章程、协作规则、状态模型和严格存档边界尚未完整建立，后来才补齐。

### B. 用第 0 关打通第一条真实玩家链

**时间：2026-07-18 至 08-01**

开发不是先做抽象框架，而是围绕第 0 关逐步贯通战场输入、命令、移动、AI、地图／全景战斗、
剧情、肖像、音乐、存档、转职和原版 UI。普通入口的无夹具通关最终成为第一个可信的垂直切片。

这一阶段验证了核心架构：

- 模拟拥有规则、回合、AI、PRNG、胜负和存档；
- Phaser／Canvas 负责地图、棋子、镜头和动画；
- DOM 负责菜单、密集文字和可访问性；
- 输入先映射为语义动作；
- 表现速度和声音不能改变结算。

同时也暴露了一个规律：原版复刻的“最后 20%”不是普通 polish。鼠标五态、菜单边框、逐字时序、
音频激活、战斗锚点和像素裁剪都需要独立证据与视觉验收。仅做到“功能可用”不足以代表切片闭合。

### C. 由第 1–3 关逼出通用边界，再暂停做架构审计

**时间：2026-08-02 至 08-07（与下一阶段部分重叠）**

第 1 关引入部署、技能、状态和新的剧情／资产组合；第 2、3 关引入固定阵容、友军军团、保护目标、
续关存档和更复杂 AI。项目同时建立调试中心、战斗／技能实验室、职业目录和按关延迟加载。

在第 4 关前，审计发现核心分层正确，但“新增一关”仍需在控制器、存档、UI、调试、表现和生成
命令里重复登记。于是先做框架收口：运行时描述符、加载清单、固定关卡构造器、当前 schema 与
历史迁移分离、语义动作目录、调试场景注册和生成命令编排。

这证明了合适的抽象时点不是项目第一天，也不是全战役结束后，而是第二、三个真实变体已经显示
重复、下一切片又确实需要复用的时候。

### D. 架构收口后没有立即追关卡，而是先闭合共性玩法能力

**时间：2026-08-04 至 08-08**

Git 历史显示，第 4 关前后的重点并不是继续增加关卡数量，而是把后续战役会反复消费的能力拉到
共享实现和独立验证面中：08-02 建立调试中心，08-03 建立技能实验室，08-04 的全地形竞技场先
覆盖 22 个职业，08-05 集中接入普通技能／状态与地图表现，08-06 补齐职业行动和全职业对战，
08-07 按技能族拆分竞技场浏览器回归，08-08 扩到 35 个普通职业并建立转职触发实验室。第 5 关
也是在这些工作之后才开始实现。

这一阶段实际闭合的是**高频共性能力**：普通职业动作、通用技能与状态、成长／转职、共享地图与
全景表现、普通 AI 可复用的动作路径、规则身份、存档和组合测试。它不是“把所有未来机制提前做
完”：专家敌军 AI 在第 7、8 关之后才统一，半龙传送、Boss 特例和后期目标优先级等仍在首次消费
它们的关卡实现。

这样做比架构收口后立刻追关卡更合理，原因有四点：

- 技能 × 职业 × 地形 × 阵营 × 状态是组合问题，在 Arena／实验室中比逐关偶遇更容易系统覆盖；
- 转职、状态、AI 和技能若随关卡各做一半，会反复改共享存档、动作协议和表现时序；
- 先冻结高频能力接口，后续关卡就主要变成地图、剧情、编成、目标和事件的内容装配；
- 共性 bug 与逐关内容 bug 被分开，失败时更容易判断应回到规则层还是关卡合同。

因此准确的经验不是“垂直切片后一次性实现全部玩法”，而是：先用两三个变体发现边界，完成架构
审计，再依据完整战役能力矩阵闭合高频共性能力；稀有和 Boss 专属机制保留到首次消费切片。

### E. 通过能力收口门后，按“规格／实现”对扩展完整战役

**时间：2026-08-08 至 08-15**

通过共性能力收口门后，项目把后续工作组织为成对里程碑：先闭合逐关证据和纸面合同，再对该关
有限授权，实现后运行定向规则、浏览器、视觉和构建门禁，再由用户接受并开放下一边界。

每关不只登记开局模板，还逐步形成以下固定检查面：

- 关前剧情、部署候选和固定棋盘单位；
- 敌我军团、主将、AI 与目标；
- 回合事件、动态生成、击杀替补和形态转换；
- 胜负优先级、失败重试、胜利保存和下一路由；
- 两套代表性成长档、深层转职和新入队角色；
- 关前、部署、玩家回合、近胜、近败、胜利准备和完成路由调试场景；
- 当前版本存档、旧版本迁移和非法存档拒绝。

由于高频能力已经在实验室和共享目录中闭合，这一阶段大量工作转为地图、剧情、编成、目标和逐关
事件装配；但每关仍需生成运行时内容、登记存档与调试场景、补定向测试，并不是字面上的“只导入
地图和剧情”。这种结构让关卡可以快速推进，又不把“上一关写法”误当作下一关事实。结局和隐藏
关也作为独立垂直切片处理，没有因为最后一个战斗完成就假定项目已经完成。

### F. 全战役可玩之后进入产品化，而不是立即发布

**时间：2026-08-15 至 08-22**

这一阶段集中补齐启动、标题、完整结局、制作人员表、原版点阵字体、菜单动画、存档备份、图鉴、
响应式覆盖层、背景选择、音频调度、像素缩放和桌面高 DPI。用户试玩仍持续发现 AI 路径、动画
锚点、原版怪癖与复刻修复边界的问题，说明“内容齐全”与“产品可交付”是两个里程碑。

也是从这时起（08-14 之后），工作单位从“关卡里程碑”变成了“决定编号”。`REMAKE-088`–`123` 这一批里约有
20 条是平衡决定：冰雪在 08-16 一天之内改了三版（落点冰封 → 八向外推 → 试玩后收回四向），四阶近战职业的
特性，以及每关 99 回合的上限。平衡从此成为一条独立的工作线，一直延续到 1.0（见 J 节）。

随后进行两阶段资源工程：先把大量零碎帧图集化，再建立资源清单、按表面／关卡分包、加载进度、
失败重试、对象 URL 租约、图片／音频解码门、预取和缓存。实际回归证明，`fetch` 完成不代表
Phaser、CSS、`<img>` 或 Web Audio 已可无等待使用；加载页收起后的动态 import 或二次请求会让
慢网玩家看到无提示空白。

### G. 最后完成发布、桌面包与素材供应链

**时间：2026-08-20 至 08-25**

项目建立 Cloudflare Pages 发布手册、可审计玩家包、资源哈希、线上冒烟与回滚流程，并生成
Windows Tauri 安装包（之后每版随网页版一起更新，至今未签名，也未在真实 Windows 上验收）。随后把原版素材
迁到私有仓库、重写公开 Git 历史，并修复干净检出 CI。

这一步暴露出最大的流程债：不少测试和文档检查默认维护者本地存在被 gitignore 的 `reverse/`
与 `ref/` 产物，公开仓库的干净检出无法复现；浏览器 e2e 的本地 macOS 时间预算也不适合 Linux
软件渲染。最终才明确区分：

- 维护者完整证据环境；
- 无原物／无私有证据的干净检出；
- 有私有素材凭证的 CI；
- 外部 fork PR；
- 本机发布前完整 e2e；
- Web 与桌面发布包。

这些环境不是同一个门禁的不同机器，而是能力和权限不同的交付层。

初版复盘写到这里就结束了，把发布当成了终点。实际上首次部署之后还有两个半月、140 个提交和 16 个版本。

  Linux 软件渲染。之后 e2e 只作为手动触发的工作流，发布前在本机完整运行。

### I. 证据层也会错

这段运营期最有价值的教训是：错的不只是实现，取证本身也会错，而且错误会一路写进玩家说明。

- **全景战斗按原版重放（09-27）：** 用户附原版截图指出倒地姿势错位。重新反汇编后发现，导出器把出手方的落点表
  套到了受击帧上，296 帧里错了 279 帧，水平最多差 144 像素。早先为此写的“原版素材缺陷”补偿，以及迅龍騎士
  “格挡悬空”的修正条目，其实都是复刻自己读错了。0.12.0 撤下了那条错误的玩家说明。
- **原版调试模式（10-01）：** 玩家提起原版用小键盘组合键加字母键打开调试，而旧笔记写着“发布版不可达”。实现分三
  批完成；做技术测试功能时，又发现导出器解析目标阵营筛选链出错，挖出六处技术规则冲突（`REMAKE-176`–`180`）。
- **关卡名（`REMAKE-158`）：** 生成器按记录号顺推关卡名，有四关错位，改为读原版底条记录。
- **需求理解也会错：** 用户要求中毒削去首领当前生命的 1/3，第一版实现成剩下 1/3（`REMAKE-124`），用户纠正后改为
  `REMAKE-144`。之后的约定是：分数一律指扣掉的量，实现前把具体数字读回给用户确认。

### J. 平衡性优化

**原则：**

- 规则分为 `originalFacts`、`stableRemake`、`legacyStrict` 三层；平衡决定标 `[DD]`，不改 `reverse/`；
- 用户在 09-15 定下：用户要求的、偏离原版的改动都按 bug 修复处理，两套规则一起改，进「Bug 修復」分页；
- 平衡分页的条目只改 `stableRemake`，例如回合上限、敌方成长步长，`legacyStrict` 仍保留原版；
- 难度首尾两档尽量保持原版数值，中间两档承担重做；
- 改变规则就升级存档身份并写迁移。

**方法：**

- 双方 AI 对战的无头扫描：全部关卡夹具 × 两档难度，约 5 分钟跑完。以每名敌人每关得到的经验为指标，测出一转、
  二转敌人有 5%–22% 在一关内至少升一级；改步长后二转敌人降为 0；
- 多种子对比：第 3 关编组（`REMAKE-182`）用 4–6 个随机种子，对比两个候选方案；
- 临时模拟：第 29 关（`REMAKE-157`）测出最高难度到第 99 回合时首领仍停在 32 个形态中的第 3 个，于是把上限放宽到 199。

**根因优先：** 敌方成长过快（`REMAKE-159`）的根因，是把原版 3 级后的“+100”当成了每级经验步长；它其实是距离转职
还差多少的倒计时。

**玩家说明：** 游戏内「復刻說明」分三页：Bug 修復、平衡性調整、功能增強。改回原版的条目不进说明，因为原版本来
如此。

### K. 多会话协作：事故与对策

协作规范设定的默认模式是一个主 Agent 负责全部写入、按需加一两个只读子 Agent；实际上常有多个会话同时写同一个
检出，或开并行 worktree。真实发生过的事故：

- 一次 `git stash` 把另一个会话正在写的改动一起收走，另一次诊断命令里误带 stash 收走了几十个已完成文件；
- 两个 worktree 同时占用 `REMAKE-167` 和同一个验收编号；
- worktree 缺少被 gitignore 的证据目录，生成器和内容测试像回归一样失败，于是写了补链脚本；但链接过去的证据目录是
  活的，别的会话一重新生成，内容测试就整片失败；
- Playwright 悄悄复用默认端口上的服务器，从 worktree 跑的测试实际测的是主检出，有一次那个端口还被无关项目占着；
- 回合结束时工作区被整体自动提交，临时测试文件进了历史。

对策都写进了协作规范和蓝图（禁用 stash、新编号先查所有 worktree、独立 e2e 端口、补链脚本、临时文件回合内删掉、
按编号顺序合并回主线并核对生成器输出）。

AI 用量只统计到 08-23：两个 Agent 共 170 个会话，含缓存命中约 127 亿 token，净消耗约 3.5 亿。Claude Code 69 个
会话，占净消耗 28.5%、输出 60%；Codex 101 个会话，占净消耗 71.5%。08-23 之后没有再统计——这本身也是一条教训。

### L. 1.0 门：从复刻转向增强

10-26／27 按玩家反馈做了最后三条平衡修复（第 3 关右翼编组、第 9 关多莉、第 11 关麗蘭特，`REMAKE-182`–`184`）和
水战士分裂后的存档修复，随 11-08 的 1.0.0 一起发布。到这时：

- 原版可达的全部战斗、过场与结局都已由 M02–M75 逐关实现；
- 存档身份从首个切片后的 v5，经 08-25 的 v93、0.3.0 的 v109、0.15.0 的 v130，到 1.0.0 的 v133，每一步都有迁移；
- 决定日志从 08-25 的 122 条增长到 1.0.0 的 182 条；
- 隐藏关 stage 38 已通过自动与视觉门禁并随版本发布，但还没有用户普通入口的试玩记录。

规则打磨的边际收益已经很低，而第一轮留下的基础设施（证据身份、生成器、私有素材供应链、可选偏好、实验室）正好
可以承载原版没有的内容。1.0 的主版本号就是因为全套交响改编而升的，项目由此进入第二轮。

## 3. 从记录中抽出的实际工作循环

### 单个系统或关卡

```text
定位原版入口
  → 解析静态数据与代码路径
  → 实机／录像交叉验证
  → 登记 Evidence 与未知项
  → 作 stableRemake / legacyStrict 决定
  → 写系统／关卡合同与 Given-When-Then
  → 获得有界授权
  → 生成运行时内容
  → 先实现确定性模拟，再接表现与 UI
  → 添加调试夹具或实验室
  → 定向单元／浏览器／视觉验证
  → 普通入口人工接受
  → 更新状态、风险、存档身份和下一冻结边界
```

### 跨切片扩展

```text
完成 2–3 个真实变体
  → 统计重复登记、巨型分支、加载与存档热点
  → 只抽取已经重复且下一切片需要的边界
  → 用既有切片做特征回归
  → 建立完整战役内容图与能力矩阵
  → 闭合高频共性技能／职业／状态／转职／普通 AI
  → 用 Arena／技能／转职／调试场景做组合验收
  → 以后续关卡空装配演练确认“内容占主导”
  → 冻结共性能力接口，再批量扩展
  → 稀有与 Boss 专属机制在首次消费切片闭环
```

### 发布与运营

```text
功能接受
  → 候选版本冻结
  → 干净检出与证据环境分别验证
  → 生成内容、资源清单和玩家包
  → 审计包体、入口、哈希、许可证与调试面
  → 本地预览真实发布目录
  → 明确授权后部署
  → 线上冷缓存冒烟
  → 记录版本、回滚点和已知限制
```

### 发布后修补循环

```text
玩家／用户试玩反馈
  → 用调试夹具或无头模拟复现
  → 归类：实现 bug ／ 提取或笔记误读 ／ 原版缺陷 ／ 平衡问题 ／ 便利需求
  → 反汇编、实机截图或录像取证；或作产品决定
  → 分配决定编号，写明进哪套规则、进玩家说明哪一页
  → 修复前失败的回归测试
  → 存档身份与迁移
  → 随下一版发布，用户确认后转为 accepted
```

## 4. 最值得保留的做法

1. **事实、决定、合同、实现分层。** 这阻止了“代码已经这样写”反向变成原版事实。
2. **冻结边界与有界授权。** 每次只解冻一个系统或关卡，避免顺手实现未知规则。
3. **模拟与表现分离。** 大量动画、音频和 UI 修正没有改动战果或存档语义。
4. **生成器承担重复真值。** 地图、对白、职业、肖像、字体、图集和资源清单不靠多处手抄。
5. **普通入口与实验室并存。** 实验室提高组合验证效率，普通入口防止只在夹具里可用。
6. **批量扩展前闭合高频共性能力。** 能力矩阵与独立实验室让后续关卡以内容装配为主。
7. **定向自动门禁加人工视觉接受。** 既控制日常成本，又没有用 DOM 断言代替 Canvas 视觉。
8. **用户反馈回到证据和决定层。** 试玩问题不是直接改坐标，而是先判断原版事实、复刻修复还是 bug。
9. **历史存档逐版本迁移。** 规则变化有明确身份，旧版本含义没有被原地改写。
10. **固定格式的版本发布。** 每版写清存档身份、资源清单身份和决定编号，发布同时是验收节点。
11. **平衡靠扫描和数字，不靠感觉。** 双方 AI 扫描、多种子对比和改前改后数字让平衡决定可复查。
12. **撤回错误的玩家说明。** 发现是复刻自己读错时，公开撤回条目，而不是悄悄改掉。

## 7. 下一项目建议节奏

1. **第 1 周：** P0–P1，完成章程、权限分层、原物哈希、可重建工作副本和 clean-room 空仓门禁。
2. **首个切片前：** 只解析该切片需要的格式，同时建立 Evidence、Decision、Spec 和生成器模板。
3. **首个切片：** 打通普通入口、一次核心循环、一次保存恢复、失败／胜利和发布目录预览。
4. **第 2–3 个变体：** 观察重复，不提前抽领域框架；第三个变体前安排结构、存档和资源审计。
5. **共性能力收口：** 建完整能力矩阵，集中闭合高频技能、职业、状态、转职和普通 AI，用独立
   实验室完成组合验收，再以后续两关做空装配演练。
6. **批量扩展期：** 规格／授权／实现成对推进，主要装配地图、剧情、编成、目标和事件；稀有机制
   在首次消费关卡闭环，持续跑内容覆盖矩阵与代表性成长／存档路径。
7. **功能完成后：** 单独进入 hardening，不把新玩法与资源、响应式、辅助功能、发布修复混在一起。
8. **发布候选：** 从干净检出重建、审计真实玩家包、冷缓存冒烟、备份与回滚演练。
9. **首发后：** 进入版本化运营，按固定模板小步发布；反馈先分类再修，平衡用扫描和数字说话。
10. **1.0 门：** 原版内容没有已知阻断问题、存档迁移完整、玩家说明与规则一致后，冻结版本身份、归档证据和工具、
    记录返工来源，更新下一项目蓝图，再决定是否进入第二轮增强。

最核心的结论是：复刻项目的可复用资产首先是“证据到发布的流程”，其次才是工具，最后才是
领域代码。下一款游戏应复用门禁和交接格式，但重新证明它自己的规则、内容图、资源格式和体验。

## 9. 讲述素材

### 9.1 一条可以讲的故事线

1. **先取证，不先选框架：** 从 DOS 原物、字节和反汇编开始，为什么“原版事实”和“复刻决定”必须分开存；
2. **一条真正的垂直切片：** 第 0 关从标题到通关存档，以及“最后 20%”的像素与时序；
3. **什么时候抽象：** 第 1–3 关逼出框架审计，再用实验室一次闭合共性能力；
4. **内容装配期：** 规格／实现成对推进，几十个关卡如何不变成复制粘贴；
5. **发布不是终点：** 16 个版本、平衡扫描、玩家反馈；
6. **我们修了一个原版不存在的 bug：** 全景战斗落点表的故事，以及“发布版不可达”的调试模式；
7. **AI 协作的真实样子：** 两个 Agent、上百个会话、stash 和编号事故，以及哪些判断只能由人来做。
