# 第一轮“复刻”蓝图：从原物到 1.0

版本：0.4（2026-11-25）

来源：《天使帝国 II》Web 重制版第一轮的全周期复盘——从原物逆向、首个垂直切片、完整战役、产品化、
Web 发布、Windows 安装包和素材供应链，到 0.2.0–0.16.0 的版本化运营与平衡调整，直到 1.0.0（2026-07-13
至 2026-11-08）。实际演进、返工来源和本版修改理由见
[`round-1-remake-retrospective.md`](round-1-remake-retrospective.md)。1.0 之后加入原版没有的现代内容，属于第二轮，
见 [`round-2-enhancement-blueprint.md`](round-2-enhancement-blueprint.md)。

本文件保存下一款游戏可直接复用的方法、门禁和角色边界，不保存《天使帝国 II》的原版事实。新项目启动时应
复制并按目标游戏裁剪本文件；不要把当前项目的 DOS 地址、资源编号、关卡类型或领域模型当成通用框架。

## 1. 核心原则

单个系统或关卡使用以下内循环：

```text
Evidence → Decision → Contract → Generate → Implement → Verify → Accept
证据       产品决定     纸面合同     生成内容      实现        自动验证    人工接受
```

项目整体另有一条外循环：

```text
Baseline → Slice → Consolidate → Close Core → Scale → Harden → Ship → Operate → Learn
建立基线     垂直切片    变体与收口       共性能力闭合     成组扩展    交付硬化     首发    版本化运营   归档复盘
```

`Operate` 是 0.3 版没有的阶段：首次发布不是终点。本项目首发之后又用了约两个半月、140 个提交和 16 个版本，
处理试玩反馈、原版贴合和平衡调整，才到 1.0。

九条不可破坏的边界：

1. 原版事实、复刻产品决定和当前实现分别维护，不能互相覆盖；
2. 原始介质只读，所有实验都在可重建副本上进行；
3. 数值、地图、对白和资源目录由机器产物生成，不在设计与代码中手抄多份真值；
4. 实现者不能替产品决定 `[TBD]`，AI 之间的共识也不能代替证据；
5. 规则、随机、存档和 AI 属于可序列化模拟，渲染、动画、声音和 UI 不成为玩法真值；
6. 自动验证证明合同未漂移，人工试玩判断节奏、手感、可发现性和最终接受；
7. 维护者完整证据环境、无原物的干净检出、私有素材 CI、外部 PR 和发布环境分别定义能力，
   不假定任何机器都拥有本地 `ref/`、`reverse/`、凭证或专有素材；
8. 开发构建、测试夹具和实验室不是玩家包；只有可重建、可审计、可回滚并通过真实入口冒烟的
   发布产物才算交付；
9. 证据层本身也会错：提取器和取证笔记要像代码一样测试，宣称“原版 bug”之前要有第二份独立证据
   （实机截图、录像或另一条代码路径）。

## 2. 从立项到交付的阶段

### P0：项目章程与可行性

建立一页 PRD-lite，至少回答：

- 复刻为何存在，目标玩家是谁；
- 目标平台、输入设备、分辨率和浏览器／系统范围；
- 忠实度维度：规则、剧情、像素、音画时序、UI、存档与原生怪癖；
- 明确非目标，例如联网、移动端、Mod、全平台或新增内容；
- 原始素材、商标、音乐和发布权限的来源与使用边界；
- Web／桌面／离线包等交付渠道、私有素材取得方式、外部贡献者可运行到什么程度；
- 冷启动、请求数、包体、内存、帧率、输入延迟和最低可访问性的初始预算；
- 成功标准、首个垂直切片、发布图、停止条件和回滚责任人。

退出条件：范围、证据来源、法律／分发边界、目标环境、非功能预算和首个切片得到人工确认；
禁止在权限模型未定时把受限原物直接提交进计划公开的 Git 历史。

### P1：冻结原物与建立清单

建议目录：

```text
ref/original/          # 永久只读的原始文件
reverse/work/          # 可丢弃、可重建的实验副本
reverse/manifests/     # 原物和关键生成物哈希
reverse/captures/      # 截图、录像、音频、输入轨迹、存档样本
private-assets/        # 可选；受限素材的独立仓库／包，不进入公开历史
```

最低产物：

- 文件树、大小、时间戳和 SHA-256；
- 可执行模块、资源容器、配置、存档和字体的初步分类；
- 能重复启动原版的模拟器／兼容层配置；
- 标题、首个可玩状态、一次胜负和一次存读档的基线捕获；
- 原始输入永不直接作为工具的写入目标；
- 明确哪些产物可提交、哪些只在维护者环境存在、哪些由私有供应链注入；
- 在一个没有原物、没有本地逆向产物的新检出中运行最小安装、类型检查和构建，记录预期跳过项。

退出条件：另一台获授权机器能重建同一工作副本与基础捕获；无授权的干净检出也能明确地完成
其承诺的最小门禁，而不是因隐含本地文件随机失败。

### P2：把逆向做成编译管线

推荐数据流：

```text
raw bytes
  → extracted records
  → decoded structures
  → normalized machine JSON
  → rendered/contact-sheet evidence
  → generated runtime content
```

每个解析器都应具备：

- 明确输入哈希与格式版本；
- 严格长度、边界、枚举和引用校验；
- 能在失败时指出记录号／偏移，而不是静默容错；
- 代表性 fixture 或黄金摘要；
- 可重复输出，连续运行不产生 diff；
- 对未知字节保留原值，不急于命名或赋予玩法语义；
- 把输入身份、生成器版本、输出身份和运行时消费者串成可审计清单；
- 生成内容与浏览器运输内容分层：开发／证据源可保留逐帧文件，玩家包可以由生成步骤图集化、
  分包或压缩，但不能手工改发布目录；
- 提取器的解析顺序、表选择和分支要有独立回归：本项目曾因导出器把出手方落点表套到受击帧上，
  在 296 帧里错了 279 帧，又据此写了一条“原版素材缺陷”的补偿和玩家说明，后来全部撤回。

不要先写一个覆盖所有资源的巨型提取器。优先闭合首个垂直切片实际消费的地图、单位、
对白、音效、动画和存档；发现共同格式后再提取共享工具。

### P3：建立证据层

证据登记建议使用机器可读记录，并生成玩家可读表格：

```yaml
id: BAT-001
claim: 普通攻击伤害公式与取整顺序
confidence: confirmed
sources:
  - kind: disassembly
    location: module-29:1234
  - kind: runtime-capture
    artifact: captures/battle-seed-001.json
consumers:
  - design/systems/combat.md
unknowns: []
```

最低置信等级：

- `confirmed`：代码、数据或实机可以直接支持；
- `supported`：多项间接证据一致，但仍含人工解释；
- `hypothesis`：可测试假设，不得直接成为默认玩法；
- `unknown`：尚未闭合。

原版 GDD 只描述证据支持的行为。取证缺口、低层原设计名和无法恢复的未定义行为必须显式
保留，不用现有实现补写原版历史。

“发布版不可达”“原版本来如此”这类否定性结论尤其要有来源。本项目的旧笔记曾写原版调试模式在发布版中
不可达，后来玩家提起原版的秘技按键，才发现它一直可以打开；实现它的技术测试功能时，又挖出六处技术规则
证据冲突。返工统计里应单列“提取或笔记误读”一类，它和实现 bug 的修法不同。

在逐关、逐章节或多形态游戏中，再建立“内容覆盖矩阵”。同一角色、单位、事件或资源至少交叉
检查：静态模板、名单／选择界面、回合事件、动态生成、击杀替补、形态转换、对白／肖像和结局
统计。即使结论为“没有增援／没有分支”，也要登记已经排除的通道；否定性结论不能只根据开局
画面或一张静态表推断。

### P4：建立复刻产品层

将规则至少分为：

- `originalFacts`：原程序和资源实际做了什么；
- `stableRemake`：默认复刻体验及已批准 bug 修复；
- `legacyStrict`：安全、确定且值得保留的怪癖兼容；
- `modProfile`：显式开放的覆盖点。

每个偏离原版的决定都要有稳定 ID，记录：原版事实、玩家影响、默认选择、严格兼容选择、
存档／随机影响、UI 反馈和验收场景。不能为“代码更好写”而修改玩法。

立项时就写清规则集政策，不要等第一百条决定时再补：

| 改动类型 | `stableRemake` | `legacyStrict` | 玩家说明 |
| --- | --- | --- | --- |
| 改回原版（复刻实现或提取器与原版不符） | 照原版 | 照原版 | 不立条目，原版本来如此 |
| 修原版缺陷，或用户明确要求的偏离 | 修 | 一起修 | 「Bug 修復」 |
| 平衡调整（回合上限、成长步长、编组） | 改 | 保留原版 | 「平衡性調整」 |
| 现代便利（不改结算） | 加 | 加 | 「功能增強」 |
| 怀旧开关（让玩家切回原版结算） | 设备级偏好，默认关 | 不需要单独实现 | 与对应修复条目合并说明 |

怀旧开关的边界：只存设备偏好，不进存档、不升级保存身份；规则只有一份实现，由一个选项切换，AI 规划缓存的
签名要包含它；竞技场和实验室不显示也不读它。决定编号由脚本分配，CI 检查重号和悬空引用——本项目有两个并行
会话抢过同一个编号，也有几条编号只在状态表里出现、决定日志里没有。

### P5：规格先于解冻

系统规格至少包括：

1. 玩家目的与可感知结果；
2. 触发条件、合法输入、合法目标、取消边界和提交时点；
3. 校验、随机、取整、结算、状态更新和后续消费者的严格顺序；
4. AI 是否复用同一动作规则；
5. UI、音画和可访问性反馈；
6. 保存／读取、失败、终局和版本边界；
7. `stableRemake / legacyStrict / Mod` 差异；
8. Given／When／Then 验收；
9. 原版证据和产品决策链接；
10. 资源准备、加载失败、冷缓存、音频激活、响应式／缩放和目标平台的非功能边界。

关卡规格应按玩家时间轴覆盖：关前剧情、部署、初始棋盘、回合事件、胜负、终局、保存、
路由、UI 状态、表现设置独立性和下一个冻结边界。

退出条件：获授权切片不存在实施必需 `[TBD]`。

### P6：先完成一条真正的垂直切片

首个切片应贯通：

```text
启动 → 标题／载入 → 剧情 → 准备／部署 → 核心玩法 → 胜负 → 保存／路由
```

它需要验证最危险的架构假设，而不是只挑最容易实现的画面。浏览器 2D 游戏默认边界：

- 模拟拥有单位、规则、回合、AI、胜负、PRNG 和可保存状态；
- Phaser／Canvas 拥有地图投影、精灵、镜头、动画和效果；
- DOM 拥有密集文本、菜单、设置和可访问性表面；
- 物理输入先映射为 `move / confirm / cancel / pause` 等语义动作；
- 动画速度、声音、减少动态和跳过演出不能改变模拟结果。

首个切片还必须从交付角度闭环：

- 普通入口冷启动，不依赖 `?test=1`、调试 API 或预热缓存；
- 一次保存、刷新／重启、读取和继续，非法存档有玩家可见反馈；
- 写入前先按读取规则校验，读不回来的记录不写入、不覆盖原槽。本项目到 0.8.0 才补上写入校验，此前同一类
  “存了读不回”的缺陷三次到了玩家手里；补上后用无头脚本在全部关卡夹具 × 两档难度上存读约 5000 次，又找出
  两个 bug。这套存读往返脚本应从第一个切片起就进仓库；
- 图片、字体、音乐、音效和延后加载模块在加载页收起前真正可用，不只完成 `fetch`；
- 浏览器音频激活、解码失败、资源失败与重试有明确状态；
- 从干净检出生成第一份真实玩家目录并本地预览，确认调试入口、实验室和私有证据未进入包；
- 记录首屏字节、请求数、解码内存和目标设备表现，作为后续扩展预算的基线。

### P7：按能力切片扩展，并在批量关卡前闭合共性能力

后续里程碑按“首次建立并验收一种能力”组织，例如首个部署、首个状态生命周期、首个特殊
目标、首个动态地形、首个跨关存档，而不是只按关卡编号或完成百分比组织。

推荐状态机：

```text
frozen → specified → authorized → in-progress → implemented → verified → accepted
```

- `specified` 只表示纸面闭合，不自动授权代码；
- `implemented` 表示实现和约定的局部门禁已完成，仍可能等待完整技术或人工验收；
- `verified` 表示约定的自动技术门禁通过；
- `accepted` 表示必要的人工试玩或产品决定通过。

先完成两至三个能暴露不同能力的真实变体，再进行架构审计；只提取已重复出现且下一切片确实
需要的通用边界。审计结束不等于可以立刻批量推进关卡。

审计至少检查：新增内容需登记的模块数量、控制器／存档巨型分支、跨层依赖、生成器重复、调试
夹具覆盖、按关资源边界、首屏／当前切片预算和旧存档迁移成本。不要只看代码行数；重点是同一
语义身份是否在多个装配点重复选择。

在批量扩展前建立两张全局图：

- **内容图：** 所有可达章节、分支、结局、隐藏内容、跳号、返回边和不可达槽；
- **能力矩阵：** 每关会消费的动作／技能、职业／成长、状态生命周期、普通 AI、目标、事件、
  表现、存档语义和调试入口，并标出“共性高频”“稀有”“Boss／关卡专属”。

随后安排一次**共性能力收口冲刺**。它的目标不是预先实现所有未来机制，而是把矩阵中会被多关
复用的高频能力一次做完整，并在不依赖战役进度的调试表面中完成组合验证。适合这一阶段闭合的
通常包括：普通职业与动作目录、通用技能和状态、转职／成长触发、普通 AI 与目标选择、共享表现、
规则身份和存档序列化。只出现一次的稀有机制、Boss 特例和后期独有事件仍在首次消费它的已授权
切片中实现，避免把“能力收口”变成新的前置大框架。

共性能力收口门至少要求：

1. 能力矩阵中所有“共性高频”项都有证据、合同、稳定语义 ID、实现与定向测试，未完成项显式冻结；
2. 同一动作规则能被玩家、AI、战役和实验室复用，不以逐关分支复制一套近似实现；
3. 技能／职业／状态／转职／普通 AI 的代表性组合已在 Arena、技能实验室、转职实验室或等价调试面
   验证，且实验室不读写战役记录；
4. 用至少两份后续关卡规格做“空装配演练”：若仍需改共享模拟、存档或表现协议，则门禁失败；
   若主要只需增加地图、剧情、编成、目标和逐关事件等内容描述，则可以进入批量扩展；
5. 通过普通入口复验一个既有切片，证明能力收口没有让真实玩家链退化，然后冻结共性能力接口。

通过门禁后，关卡推进应变成**内容占主导的装配工作**，而不是字面上的“只导入地图和剧情”。
每个切片仍需覆盖“真实新开／继续或迁移／失败重试／完成路由”，成长型游戏仍需代表性成长与
深层分支档；新增稀有能力仍按 Evidence → Decision → Contract → Implement → Verify → Accept
闭环。调试夹具提高验证效率，但不能替代无夹具的普通入口。

### P8：交付硬化与发布

功能齐全后单独进入 hardening，不再混入未经授权的新玩法。最低工作包：

- 资源图集、清单、分包、缓存、对象 URL／纹理租约、解码并发和释放策略；
- 冷缓存、慢网、失败重试、重复请求、场景切换和长会话内存验收；
- 原版字体、窗口构件、锚点、裁剪、调色板和音画时序的最终 Presentation Bible 审计；
- 键盘、鼠标、手柄、音频激活、缩放、减少动态、不同宽高／DPI 和目标浏览器矩阵；
- 存档导出／导入、历史迁移、未来版本拒绝、完成档和结局后语义；
- 从干净检出生成玩家包，审计文件数、单文件／总体积、哈希、许可证、入口和调试面排除；
- 本地预览真实发布目录，再在明确授权后上传预览或生产，并做线上冷缓存冒烟。

发布候选门禁与日常开发门禁分开。发布前可以运行全量测试；普通改动仍运行最低充分的定向测试。
性能预算优先使用稳定工作量指标（寻路图构建次数、请求数、解码集合、资源字节），墙钟只在固定
环境作为补充，避免把 CI 软件渲染慢误判成算法回归。本项目把浏览器 e2e 从 2 个分片提到 8 个后第一次在 CI
上跑完，113 个失败全是按 macOS 调校的超时撞上 Linux 软件渲染；最终 e2e 只在本机发布前完整运行，CI 只跑
不依赖时间预算的门禁。

### P9：版本化运营——试玩反馈、原版贴合与平衡

首发之后的工作单位从“关卡里程碑”变成“决定编号”。每个问题先判断归属，再走对应的链：

```text
玩家／用户反馈
  → 复现（调试夹具或无头模拟）
  → 归类：实现 bug ／ 提取或笔记误读 ／ 原版缺陷 ／ 平衡问题 ／ 便利需求
  → 证据（反汇编、实机截图、录像）或产品决定
  → 决定编号与规则集归属（见 P4 的表）
  → 修复前失败的回归测试
  → 存档身份与迁移
  → 版本发布，发布后确认才转为接受
```

版本节奏与发布说明：

- 用脚本统一版本号（本项目 0.2.0 起才有明确的递增规则，此前一直是 0.1.0）；
- 每版发布说明固定字段：源码基线、存档身份与迁移、玩家可见改动（附决定编号）、玩家说明新增条目、资源清单身份、
  素材仓库同步到的提交、各渠道产物与校验文件；
- 发布兼作验收：版本上线、用户确认之后，才把对应条目转为 `accepted`；
- 发布前检查有固定配方：文档、证据基线、类型检查、覆盖率、构建、发布构建、素材哈希、`git diff --check`，然后在
  独立端口跑完整 e2e，再对真实发布目录跑玩家流程冒烟；主线在检查后有新提交就重跑。

平衡调整：

- 首尾两档难度尽量保持原版数值，中间档承担重做；
- 每条平衡决定附改前改后的数字，不只写“更合理”；
- 平衡工具进仓库：双方 AI 对战的无头扫描（本项目约 5 分钟跑完全部关卡夹具 × 两档难度）、多种子对比、固定种子；
- 先找机制根因再调数：本项目的敌方成长问题，根因是把原版“距离转职还差多少”的倒计时误当成了每级经验步长。

现代便利功能（自动配置、小地图拖曳、删除存档槽、画面内指针等）只改操作、不改结算，进玩家说明的「功能增強」。
它们与第二轮的增强内容不同：不需要生成素材，也不需要可选层。

退出条件（“1.0 门”）：原版可达内容没有已知阻断问题，存档迁移链完整，平衡决定都已发布并经用户确认或明确
挂起，玩家说明与实际规则一致。通过后才进入第二轮增强。

### P10：封版、归档与学习

- 给代码、内容、规则身份、存档 schema、玩家包和资源清单建立不可变版本对应；
- 保存 SHA-256、部署 ID、下载说明、已知问题、支持边界和可演练的回滚点；
- 归档原物哈希、工具版本、关键捕获、接受记录和未解未知项；
- 区分“已完成产品”“仍需权利人许可／签名／特定平台实机复验”的事项；
- 从 Git、里程碑、缺陷和发布记录统计返工来源，更新本蓝图和模板；
- 持续采集 AI 用量和提交署名，不要只在中途统计一次；
- 只抽取经第二款游戏验证仍通用的领域代码，流程与生成／验证工具可以先抽取。

退出条件：指定版本可由获授权环境重建、验证、安装／访问和回滚；下一项目蓝图已吸收本次新经验，
而不是仍停留在中途快照。本项目 0.3 版蓝图写在首次部署后不到十天，漏掉了之后两个半月的运营经验，这次才补上。

## 3. 测试与验收策略

不同对象使用不同证据：

| 对象 | 首选证明方式 |
| --- | --- |
| 格式解析、资源目录、生成器 | fixture、哈希、schema、重跑无 diff |
| 公式、网格、AI、PRNG、存档 | 单元、性质测试、种子回归、迁移矩阵 |
| 模拟与表现集成 | 确定性场景、语义事件、浏览器流程 |
| Canvas／WebGL、HUD、动画 | 代表性截图、关键帧、人工视觉检查 |
| 音乐、音效、逐字音 | 请求时间线、音频哈希／波形、实听 |
| 启动到结算的玩家流程 | 无测试参数、无调试 API 的普通入口通关 |
| 冷启动、分包、缓存和解码 | 网络记录、故障注入、重复请求、内存／释放边界 |
| 玩家发布目录 | clean-room 重建、包体／哈希审计、本地预览、线上冒烟与回滚 |
| 存档读写 | 写入前校验；全部关卡夹具 × 难度的存读往返扫描；修复前失败的回归 |
| 平衡与难度 | 双方 AI 无头扫描、多种子对比、改前改后数字 |
| 提取器与取证结论 | 独立回归、第二份证据（实机截图／录像／另一条代码路径） |
| 手感、节奏、可发现性 | 结构化人工试玩与接受记录 |

传统 Test-Driven Development 适合公式、解析器、PRNG、AI 和存档迁移；未知原版行为应先
做 evidence-driven characterization，避免用测试把猜测永久锁进实现。动画与音频先用实验室
闭合时间轴，稳定后再增加回归测试。

测试矩阵必须按环境写清“能证明什么”，不要用一个 `pnpm check` 假装覆盖全部机器：

| 环境 | 应承诺的门禁 |
| --- | --- |
| 维护者证据环境 | 解析器、原物哈希、生成器、证据回读和完整内容验证 |
| 无原物 clean-room | 安装、类型检查、纯源码测试、构建；依赖证据的检查明确跳过并列出 |
| 私有素材 CI | 素材身份、玩家构建、允许的自动测试；不把 secret 暴露给 fork |
| 外部 PR | 不依赖私有素材的检查，明确说明无法运行的部分 |
| 本机浏览器验收 | 定向 e2e、视觉、音频和目标平台实际性能 |
| 发布候选环境 | 全量门禁、真实玩家目录、冷缓存、线上冒烟和回滚演练 |

每个浏览器流程都应归属一个生命周期路径：新游戏、继续游戏、战中读档、失败重试、跨章节路由、
完成档、结局／制作人员表。调试直达只证明局部状态，不证明这些路径之间的协调。

调试夹具的默认名单也会掩盖问题：没有成长的夹具里大多是基础职业，转职后的棋子图和职业集合问题要用
“全部顶层职业”的成长档或随机成长档才能复现。成长档应和关卡一起登记，按入队关卡推算，而不是全员同一基线。

## 4. Game Studio 角色与交接

角色是权限和产物边界，不是人格设定，也不要求永久占用一个 Agent。

### Director / Integrator

- 控制范围、授权、优先级、风险、状态转换和最终合并；
- 只接受带证据、合同、验证与未知项的交付；
- 不让多个写入 Agent 同时拥有同一真值文件。

### Reverse Engineer

- 默认只读原物与现有设计；
- 输出解析器、机器证据、捕获和 Evidence ID；
- 不修改默认复刻规则，不把攻略或记忆升级为事实。

### Remake Designer

- 消费证据并输出规则决定、系统／关卡合同和验收；
- 可以提出 `[H]`，不能自行把 `[TBD]` 变成默认玩法；
- 不用 Web 架构解释 DOS 原版。

### Simulation Engineer

- 负责确定性规则、动作、AI、PRNG、存档和单元测试；
- 只实现已授权合同；
- 不让场景对象、动画帧或墙钟进入模拟真值。

### Presentation / Asset Engineer

- 负责运行时内容生成、Phaser、UI、音频、动画和实验室；
- 保留像素、锚点、透明、调色板和时间轴证据；
- 不改变模拟顺序来迁就表现。

### Delivery / Release Engineer

- 负责 clean-room、私有素材注入、CI 权限、资源清单、玩家包、版本、哈希、部署和回滚；
- 不手工修补发布目录，问题回到源码、生成器或打包脚本修复；
- 区分开发入口、实验室、预览和生产，不把测试凭证或调试能力带进玩家包。

### QA / Playtest

- 默认只读实现，独立复现和报告；
- 使用普通玩家入口、浏览器截图、音画事件和确定性场景；
- 每个问题包含玩家所见、复现步骤、影响和责任子系统。

适合并行：代码库探索、证据扫描、独立资源族、测试日志、视觉审计。适合串行：事实决定、
规则授权、共享 schema、同一控制器和最终合并。并行写入使用独立 worktree／分支。

### 多会话与多 worktree 卫生

本项目常有多个 AI 会话同时写同一个检出，或在并行 worktree 里各做一项。下面每一条都对应一次真实事故：

| 规则 | 事故 |
| --- | --- |
| 共享检出禁用 `git stash` | 一次 stash 把另一个会话正在写的改动一起收走 |
| 新编号先查所有 worktree 的未提交改动，或由脚本分配 | 两个 worktree 同时占用同一个决定编号和验收编号 |
| 新 worktree 第一步运行补链脚本（取证产物、原始资料、素材包） | 缺了被 gitignore 的证据目录，生成器、文档检查和内容测试像回归一样整片失败 |
| 可写的证据目录不要在 worktree 之间共享 | 别的会话重新生成证据，本 worktree 的内容测试跟着失败 |
| 每次 e2e 都用独立端口 | Playwright 悄悄复用已在默认端口上的服务器，测到的是主检出甚至无关项目 |
| 临时测试文件在回合结束前删掉 | 回合结束时工作区被整体自动提交，临时文件进了历史 |
| 合并回主线按编号顺序 cherry-pick，并核对生成器输出逐字节一致 | 并行分支的生成内容互相覆盖 |
| 旧决定条目保持原文，只加前向说明 | 后来的决定让旧条目过时，直接改写会丢失当时的依据 |

## 5. Agent 工作包

每次委派都应提供：

```yaml
id: STAGE-00-IMPLEMENT
objective: 实现已批准的第 0 关合同
state: authorized
evidence: [STAGE-001, BAT-001]
decisions: [REMAKE-001]
spec: design/stages/stage-00.md
allowedPaths:
  - src/content/stage0/**
  - src/simulation/**
  - tests/unit/stage0-*.test.ts
forbidden:
  - 解决任何 TBD
  - 修改下一关内容
acceptance:
  - S00-A
  - S00-B
commands:
  - pnpm exec vitest run tests/unit/stage0-battle.test.ts
humanGate: true
environment: maintainer-evidence
deliverables:
  - generated content identity
  - test report
  - player-visible screenshots
```

交付必须说明：已完成、已验证、未验证、剩余不确定项、范围外发现和工作区状态。Agent 之间
通过版本化文件、测试结果和证据 ID 交接，不依赖上一段聊天记忆。

## 6. 轻量专业文档集

```text
docs/
  prd.md                       # 产品目的、范围、非目标、成功标准
  original-gdd.md              # 证据支持的原版事实
  remake-gdd/                  # 默认玩家体验与规则集
  technical-design.md          # 架构、数据流、存档、输入、性能
  decisions/gameplay/          # 原版怪癖与复刻产品决定
  decisions/adr/               # 技术架构决策
  specs/systems/               # 系统合同
  specs/stages/                # 关卡垂直切片
  qa/test-strategy.md          # 测试层、浏览器矩阵、视觉政策
  qa/environment-matrix.md     # 证据环境、clean-room、CI、fork 与发布能力
  production/roadmap.md
  production/status.md
  production/risks.md
  production/release.md        # 玩家包、版本、部署、回滚和供应链
  production/release-history.md # 每版固定字段的发布说明
  player/remake-differences.md # 玩家说明，由游戏内说明内容生成
  retrospective.md
```

玩家说明只保留一个来源。本项目游戏内的「復刻說明」与仓库里的玩家文档各写一份：1.3.0 发布时后者仍写“每關
最多 99 回合”，没有两个怀旧开关，也没有第二轮的音乐、语音与高清美术，到 2026-11-25 才手工补齐；应由游戏内
内容生成文档。

另建 Asset Bible，记录来源／授权、稳定 ID、命名、坐标系、锚点、透明索引、调色板、帧序、
音频格式、转换命令和运输预算。P0 先建立一页发布骨架，固定渠道、权限、玩家包与回滚责任；
接近发布时再补具体版本策略、迁移、遥测／隐私、崩溃收集和支持细节，不需要在原型期堆积企业
文档，但也不能到封版才第一次考虑干净检出、素材授权和分发。

## 7. 自动门禁

建议从第一天提供：

```bash
pnpm docs:check            # 状态、内部链接、Evidence ID、TBD 和合同结构
pnpm content:check         # 生成器重跑后不产生 diff
pnpm test:affected         # 根据改动责任映射选择定向测试
pnpm gate:spec <slice>     # 纸面闭合门禁
pnpm gate:implement <slice># 实施门禁
pnpm gate:accept <slice>   # 自动验证与人工接受材料
pnpm cleanroom:check       # 无原物／无本地取证产物的最小可复现门禁
pnpm resources:check       # 资源身份、包归属、预算、重跑无 diff
pnpm release:verify        # 玩家包入口、哈希、体积、许可证与调试面排除
pnpm decisions:check       # 决定编号无重号、无悬空引用、规则集归属齐全
pnpm save:roundtrip        # 全部关卡夹具 × 难度的存读往返
pnpm balance:sweep         # 双方 AI 无头扫描，输出经验、回合、胜负分布
```

状态只保留一个机器真值源，README、ROADMAP 和仪表盘由生成或校验得到。CI 至少检查：依赖锁、
文档合同、其环境可访问的生成内容、单元测试、构建和浏览器语义流程；证据基线只在拥有原物的
受控环境运行，不能让干净检出因隐含文件缺失而红。黄金图更新必须先人工判断差异。

## 8. 哪些东西现在抽，哪些以后抽

第一个项目结束即可抽取：

- 目录骨架与项目章程；
- 证据、决策、系统、关卡和工作包模板；
- 状态机与文档／链接校验器；
- 可序列化 PRNG、动作日志和存档迁移原则；
- 调试场景注册、实验室 UI 壳和 Playwright 验收模式；
- clean-room、资源清单、发布目录审计和回滚模板；
- 发布说明模板、发布前检查配方和版本号脚本；
- 存读往返扫描与双方 AI 平衡扫描的驱动脚本；
- worktree 补链脚本和多会话卫生规则；
- Agent 角色说明和 PR 模板。

至少经过第二款游戏再抽取：

- 通用战斗模型、AI 框架或关卡 schema；
- 通用资源容器解析库；
- 强制所有游戏使用的 UI／场景基类；
- 统一 Mod API。

原则是先复用流程，再复用工具，最后才复用领域代码。第二款游戏会暴露哪些抽象真正通用，
哪些只是第一款游戏留下的漂亮名字。
