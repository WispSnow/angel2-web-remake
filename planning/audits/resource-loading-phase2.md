# 分段资源加载报告（第二阶段）

实施日期：2026-08-20。本阶段只修改本地开发版；依用户要求没有运行 `build:release`、没有重建
`release/`，也没有部署 Cloudflare。第一阶段图集化与包体投影见
[`resource-loading-phase1.md`](resource-loading-phase1.md)。

## 资源清单与分包

`scripts/generate-resource-manifest.mjs` 从 `public/assets/original/` 生成：

- `public/assets/original/resource-manifest.v1.json`：schema 版本、内容身份、URL、逻辑字节数、
  SHA-256、资源包归属、包依赖与战役顺序；
- `src/game/content/resource-manifest.generated.ts`：运行时固定的清单 URL、schema 版本和内容身份。

清单使用第一阶段发布清理后的最终路径：零碎全景帧、地图命中／死亡、回合切换、逐关连续
特效和地图技能源帧都不会进入清单，取而代之的是 PNG + Phaser JSON Hash 图集。开发／证据源
仍留在 `public/`，生成器只把它们排除于玩家清单，不删除来源。

当前清单身份是
`2c37ab92fbc369d6aede8feb186975e3dc50601717e0b4cf381f16edae2e7cec`，登记 1,291 个最终玩家
资源、50 个资源包、57,978,433 B；JSON 本身为 425,707 B。以后任何被登记资源改变，都必须
运行 `pnpm content:resource-manifest`。获准形成 release 时，`prepare-release.mjs` 会在零碎来源
清理完成后逐项复核 URL、字节数与 SHA-256；旧清单不能静默随新资源发布。

## 运行时顺序

1. 普通页面先显示同游戏构图一致的 DOM 加载页并读取清单与 `boot`。开场挂载后，静默后台
   读取第 0 关包；后台请求不会阻塞开场动画。
2. 新游戏建立 `GameController` 前必须等第 0 关包；若后台读取仍在进行，加载页接管同一批
   请求并按清单逻辑字节显示进度。
3. 继续游戏先通过原有严格存档校验，再以保存目标关卡通过同一资源门；完成态存档需要来源
   关运行时时，也先载入该来源包。
4. 关卡控制器在导入下一关运行时之前先等待下一关包。新关实际挂载后，清单只静默预取战役
   顺序中的再后两关；不会把全战役设为强制依赖。
5. `stage-49` 结局与 `stage-39` 制作人员表在各自 DOM 表面挂载前走独立资源门。

加载页使用原生 `<progress>`、可读状态与 `aria-live` 文字；进度以响应流累计字节／清单逻辑
字节计算。单个请求失败会保留错误 URL 与 HTTP 状态，并提供聚焦的“重试”按钮；失败项会清除
自己的 Promise 状态，重试会真实重新发请求。并发仍在收尾的请求不会覆盖失败文字。

## 内存与解码边界

- 资源包预取只流式读完响应并丢弃正文，让浏览器 HTTP 缓存承担复用；不调用
  `createImageBitmap`、`HTMLImageElement.decode()` 或 `decodeAudioData()`。
- `AudioManager` 不再把三套第 0 关音乐复制到自己的长期 encoded 缓存。`MusicTransport` 只在
  当前选择曲目且浏览器已获用户激活时解码该曲目的 entry／loop，不提前解码全战役音乐。
- `BattleScene` 不再每关把 36 个我方职业全部交给 Phaser。它只预载棋盘当前职业、其即时
  转职候选及关卡显式动态棋子；后续转职层与无关职业不会进入该 Scene 的纹理管理器。
- 没有 Service Worker、R2、全战役强制下载或音乐全量解码；地图、剧情背景和音乐仍是独立文件。

## 自动验收合同

- 单元测试逐项复算 1,291 个清单资源的字节与 SHA-256，核对包图、两关预取顺序、图集最终路径
  和零碎来源排除；另验证 Phaser 的当前职业／即时转职候选集合。
- Chromium 覆盖：开场显示时第 0 关已后台请求但第 1 关未请求；新游戏在第 0 关包完成前不挂载
  Phaser；失败页保留错误并可重试；继续游戏等待存档目标关；直接通关只强制下一关，挂载后
  才请求再后两关且不请求第四关。
- 加载进度页与失败重试页均纳入显式视觉审计；最终验证命令及结果以本次交付报告为准。
