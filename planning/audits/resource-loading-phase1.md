## 迁移结果

- 全景战斗的 777 张动作帧生成 75 组图集：每个物理侧／职业一组，公共扬尘单独一组；每组
  都是 PNG + Phaser JSON Hash。最大纹理边长不超过 1,024 px，最大单张解码内存
  1,158,912 B，没有全战役巨型纹理。运行时只在该职业帧第一次真正显示时请求对应 PNG。
- 地图命中／死亡、回合切换、第 4 关力场脉冲、第 26 关推柱共 109 张连续小帧生成 4 组
  PNG + JSON Hash。BattleScene 只预载当前关卡需要的图集。
- 帧名保留 `side/class/set/frame` 或 `asset-family/channel/frame` 的稳定语义；图集帧
  `trimmed=false`、`rotated=false`，不改透明边界。逐帧 RGBA 测试证明 886 张迁移源图与图集中
  对应区域逐像素一致。表现层继续使用原有锚点、帧序与最近邻缩放。
- 开发／证据源 PNG 全部保留。`prepare-release.mjs` 先验证每个 PNG/JSON 对存在，再只从将来的
  玩家发布目录清理已迁移的零碎文件。

### 肖像兼容结论

肖像暂不迁移。当前一笔动画肖像由 112×112 主图、三帧眼睛、三帧口型组成；眼睛和口型使用
原版表中的独立尺寸与百分比落点，主图承担可访问名称，覆盖层使用空 `alt` 与
`aria-hidden=true`。眨眼按 DOM 层透明度切换，口型按逐字事件切换。把它改成 CSS 裁片或
Canvas 会同时触及原版落点、透明边界、随机眨眼时钟、逐字口型与可访问树，470 张图仅
400,401 B，收益主要是请求数而非下载体积。风险／收益比高于本阶段可接受范围；后续若迁移，
应先建立独立的 DOM 图集裁片组件，并用 0–67 全记录像素、落点、动画和可访问性验收封口。

不是一次伪装成实测的新构建：

| 指标 | 迁移前玩家包实测 | 迁移后投影 | 变化 |

逻辑体积的小幅增长／下降不是主要目标；这里用少量 JSON 和透明 padding 换取显著减少的小文件
请求，同时限制每次纹理解码范围。

从任务开始时的 `HEAD` 临时只读副本和迁移后工作区完整播放到结束：
