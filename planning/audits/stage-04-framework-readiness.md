# 第 4 关前游戏框架审计

日期：2026-08-04

状态：`complete / refactor-verified`

范围：第 0–3 关现有 Web 运行时、模拟、内容、表现、存档、调试与生成流程。本文只评估
框架扩展成本，不解冻 `stage-04` 玩法、内容或未开放系统，也不以代码现状改写原版事实。

## 结论

现有框架的核心方向正确，不需要推倒重来：确定性模拟没有反向依赖 DOM 或 Phaser，
`StageDefinition`、事件、目标、部署、动作准备／提交、军团注册表、按关延迟加载和证据生成
都已经形成可复用边界。第 3 关新增的多军团与独立友军没有继续把槽位判断堆进控制器，
说明 `REMAKE-022` 的抽取有效。

主要问题是“通用能力已经存在，但装配层仍按关手写”。继续照第 2、3 关的接法增加第 4 关，
至少还要同步修改控制器运行时字段／加载／进入／恢复／重试分支、当前存档校验、UI 终点文案、
调试路由、动作表现命名和生成命令。每一处单独看都不大，但它们把同一个关卡身份复制到多个
模块，容易在存档、恢复或调试路径漏接。

因此建议先建立独立的 `M04.5` 架构收口，再写第 4 关纸面合同和实现。没有发现必须立即修复的
P0 正确性缺陷；下列 P1 项是为了降低扩展风险，而不是改变玩法。

## 审计方法与基线

- 阅读设计验收、M04、第 3 关合同、军团合同、原版 GDD、证据登记与复刻规则决定；
- 检查 `src/game/` 非生成 TypeScript 的导入方向、逐关条件、槽位使用、运行时注册、存档验证、
  调试入口和生成脚本；
- 对第 2、3 关内容、战斗构造和生成器进行结构差异比较；
- 生产构建检查按关 chunk、主包与 Phaser vendor 包；
- 本次量化是启发式代码审计，不把注释、测试数据中的关卡号一律判作硬编码。

## 已经做对且应保留的边界

1. **模拟／表现分离。** `src/game/simulation/` 没有导入 `ui.ts` 或 `phaser/`；动画速度、声音、
   DOM 与 Phaser 对象没有成为战果或存档真值。
2. **动作原子提交。** 普通战斗、射击和技术共用准备／表现／提交边界，表现完成前不改生命、
   经验、行动位或 PRNG。
3. **内容可追溯。** 地图、阵容、剧情和音乐从机器证据生成到运行时目录；浏览器不读取逆向工作区。
4. **通用关卡合同。** 目标、部署、故事、音乐、事件与视口已由 `StageDefinition` 数据化；
   `stage-events.ts` 和 `objectives.ts` 不含逐关规则分支。
5. **军团合同。** 玩家、独立友军和敌军军团由 `ForceRegistry` 验证成员、阵营、主将、策略和目标；
   槽位仍可作为证据内容，但不再被控制器用来推断控制权。
6. **按关加载。** 第 1–3 关内容与战斗模块已有独立生产 chunk，新关卡不必静态进入首屏主包。
7. **严格存档。** 当前和历史版本均做深层校验，非法数据安全拒绝；问题是维护形态，不是验证宽松。

## P1：建议在第 4 关实现前完成

### A. 建立统一的关卡运行时描述符与加载清单

现状：`GameController` 分别持有 `stage1Runtime/stage2Runtime/stage3Runtime` 与 Promise，分别实现
`load/require/enter`，并在事件路由、重试、完成档恢复、战中档恢复和调试直通中重复关卡分支；
`currentStageAssets` 也按关选择导出名。

建议：在控制器与逐关模块之间增加一个编排层 `StageRuntimeDescriptor`，至少包含：

- `id`、`definition`、`assets` 与 `activateContent()`；
- 延迟 `load()`；
- 从 `CampaignState` 建立战斗、从当前版本战中档恢复战斗；
- 默认焦点、初始阶段、入关／重试方式和玩家可见默认状态文字；
- 可选的部署适配器，而不是把第 1 关部署重新泛化为所有关卡必需步骤。

加载清单是允许显式维护的唯一战役装配表。增加普通固定关卡后，控制器的进入、路由、重试、恢复
和资产选择不应再新增 `stageId === ...` 分支。第 0 关的特殊脚本移动与第 1 关部署继续通过有类型
能力表达，不要求伪装成相同流程。

验收：用一个仅测试用描述符证明进入、战中恢复、失败重试和完成路由都只依赖描述符；第 0–3 关
普通入口与现有存档回归不变。

### B. 把当前存档 schema 与历史迁移拆开

现状：`save.ts` 同时保存当前 v14 类型、逐关标签／事件／职业校验，以及 v2–v13 的完整迁移链。
历史版本的逐版本分支是必要证据，不能为了“整洁”合并；但当前 v14 校验仍用嵌套逐关条件选择
标签、合法事件和敌军职业，第 4 关会继续扩大同一函数。

建议：

- `save/current-schema.ts` 只校验当前版本，逐关元数据来自运行时／存档清单；
- `save/migrations/` 保留每个旧版本的冻结类型、验证器和单步迁移，不重写旧含义；
- `save/repository.ts` 只负责槽位、JSON 解析和安全拒绝；
- 明确区分可玩 `StageId`、战役目的地 ID 与“尚未实现边界”，避免 `CampaignState.stageId` 和
  `CompletedSaveData.stageId` 各自手写不同联合。

验收：v2–v14 迁移矩阵与损坏／未来版本拒绝测试保持；给清单增加测试关卡元数据时，当前 schema
无需新增嵌套条件。

### C. 抽取固定关卡的单位与战斗构造器

现状：`stage2-battle.ts` 与 `stage3-battle.ts` 重复“继承 roster → 建立友军 → 按难度建立敌军 →
补全 campaign roster → 组装 `BattleScenario`”流程。重复代码目前仍短，但继续复制会让命名角色
经验基线、生命夹取、状态初始化或敌军难度在关卡间悄然漂移。

建议：建立纯模拟辅助器，例如 `createFixedStageBattleScenario(config, campaign)`，配置只声明语义
单位、敌军优先级、军团与关卡特有焦点；共同函数统一处理继承 roster、属性／生命、状态和
`DeterministicRng`。第 1 关交互部署保留独立 adapter，只复用共同的单位构造原语。

验收：第 2、3 关单位快照、四档难度、campaign roster、PRNG 初态和军团验证逐字不变；新增测试
关卡不复制友军／敌军对象拼装函数。

### D. 让动作与表现使用语义注册表，不再叫 `stage1*`

现状：第 2、3 关都会注册 `stage1-actions.generated.ts`，控制器和 `BattleScene` 通过
`stage1ActionPresentation()` 读取已经成为全局共用的落雷、冰雪、回復和破邪；场景还用
`stage !== stage-00` 推断是否加载“扩展动作”。资产结构用 `enemyMonk` 等逐职业可选字段判断。

建议：动作目录按稳定 `BattleActionId` 注册规则、时间线、图形与音频，场景按当前关卡实际可达动作
预加载；地图表现由 `ActionPresentationRenderer` 表或小型策略对象分派，避免在
`BattleScene.render()` 继续增长 `if/else`。关卡地图单位图使用
`Partial<Record<UnitClassId, assetKey>>`，不为每个新职业增加资产字段。

验收：删除共享运行时 API 中的 `stage1Action*` 命名；第 0–3 关动作请求、原生 tick、截图与无残留
合同不变；新动作主要新增目录项和 renderer，而不是修改逐关判断。

### E. 消除 AI 合同对 `battle.ts` 的类型回边

现状：`battle.ts` 运行时导入 `enemy-ai.ts` 和 `force-ai.ts`，后二者又从 `battle.ts` 导入
`AlliedAiAction/EnemyAiIntent` 类型，形成唯一的 TypeScript 源依赖环。它当前会在编译时擦除，
不是运行时 bug，但让未来拆分 AI 策略时继续依赖巨型战斗类。

建议：把 AI 动作、意图和规划选项移到无实现依赖的 `simulation/ai-contracts.ts`，由战斗、敌军 AI、
军团 AI 和测试共同导入。

验收：非生成源码依赖环为 0；AI 行动排序、目标筛选和 PRNG 回归不变。

## P2：可在 M04.5 后分批推进

1. **拆分 4,046 行控制器。** 不做一次性重写；先在上述 runtime seam 后，按“战役／存档协调”、
   “动作表现 runner”、“菜单与输入状态”提取无 DOM/Phaser 的协作者。UI 先继续消费现有 facade，
   避免同时改所有调用方。
2. **数据化调试中心。** `debug-scenarios.ts` 的夹具可保持逐关，但 `debug.ts` 的关卡顺序和大型
   switch 应由场景目录／factory map 生成，新增关卡只登记场景。
3. **提取第 2/3 关生成器公共库。** 共享证据读取、地形解码、阵容／故事／音乐编译、identity hash
   与输出模板；逐关文件只声明来源与原版差异。不要假定第 4 关必然固定部署。
4. **收紧核心 ID。** 当前 `StageStoryId/StageEventId/StageMusicId/StageSimulationEffectId` 在核心文件
   手写所有逐关字面量。可由关卡局部合同加注册时验证替代；保持稳定语义 ID，不退回文件路径。
5. **终点 UI 读取战役元数据。** `ui.ts` 不应把 `stage-03/04` 映射成数字和中文序数；终点卡片从
   战役清单读取当前关、目的地、显示名和冻结状态。
6. **生成命令编排。** 根 `content` 命令可从生成清单顺序运行逐关生成器；仍保留可单独运行、可审计
   的 `content:stageN` 命令。

## 哪些“硬编码”应保留

以下内容属于证据或明确设计，不应为了抽象而删除：

- 关卡内容／生成文件中的原版槽位、坐标、行为号、职业记录、音乐号、剧情号和来源哈希；
- `StageDefinition` 中每关明确的目标、事件顺序、部署方式、视口和内容 identity；
- 军团定义中的成员、主将、地形策略和目标军团；
- v2–v13 历史迁移器中的旧字段、旧标签和旧版本规则；
- 测试中用于证明原版事实或复刻决定的具体实例。

需要消除的是同一关卡身份在编排层的重复选择分支，以及已经跨关复用却仍以首个消费关卡命名的
公共 API，而不是把一切变成无约束 JSON 或通用回调。

## 建议实施顺序

1. 先补架构特征测试和测试用关卡描述符；
2. 提取 `ai-contracts.ts`，消除依赖环；
3. 建立 runtime descriptor／loader manifest，迁移第 0–3 关进入、路由、重试、恢复和资产读取；
4. 提取固定关卡构造器，迁移第 2、3 关；
5. 拆分当前存档 schema 与历史迁移文件；
6. 语义化动作／表现／单位图资产注册表；
7. 数据化调试目录、终点 UI 与生成命令；
8. 运行 `pnpm check`、证据校验、普通 `/` 第 0–3 关真实流程和代表性截图审计；
9. M04.5 单独验收后，才为第 4 关建立纸面合同并请求实现授权。
