# M00.5：转职与多关架构准备

状态：`verified`

授权日期：2026-07-27

更新日期：2026-07-28

技术验收日期：2026-07-27

## 目标

在不创建第 1 关运行时内容、部署入口或关卡路由的前提下，消除第 0 关实现中最阻碍后续扩展的职业与状态耦合，并让妮雅、希蜜在第 0 关达到士兵转职标记时完成可保存、可恢复、确定性的职业选择。

## 授权边界

本里程碑获得以下代码授权：

1. 从机器真值生成 39 职业目录与 31 条有序转职边，运行时使用稳定语义 ID；
2. 建立通用 `StageDefinition`、战役会话与战斗快照边界，并以第 0 关完成迁移验证；
3. 把 Web 存档提升为 v5，并确定性迁移既有 v2/v3/v4 第 0 关存档；
4. 实现战斗动作后的 side 1 转职扫描、强制选择、原子提交和 DOM 覆盖层；
5. 复制并加载第 0 关内四个目标职业的原版地图棋子，保证转职后地图投影正确。

本里程碑明确不授权：

- 第 1 关地图、敌我阵容、对白、部署页、关卡入口或可游玩路由；
- 射击、技术、状态的数值与表现实现；弓兵/修女仍可使用职业共有的普通攻击；
- 第二层及以后职业所需的新战斗表现资产；
- 为全战役一次性建立没有代表性消费者的抽象；
- 修改第 1 关纸面合同的玩法含义。

## 工作包

### P1：规格与证据时序

以 [`promotion.md`](../../design/remake-gdd/systems/promotion.md) 闭合动作后扫描、队列顺序、不可取消、原子提交、生命保持和终局先后。

### P2：职业内容生成

生成文件必须保留稳定语义 ID、原生记录号、五行数值、成长、行动类别、移动/防御 profile 及有序转职候选。浏览器运行时不得读取 `reverse/`。

### P3：领域边界

模拟层持有职业、单位、战役 roster、关卡 ID、行动结算和 PRNG 真值；Phaser/DOM 只投影状态与发送语义输入。第 0 关继续是唯一可运行 `StageDefinition`。

### P4：存档 v5

v5 使用语义 `stageId` 和 `classId`，验证完整 schema、内容身份与职业存在性。v2/v3/v4 的数值职业记录确定性映射为语义 ID；未来版本、损坏 ID、非法位置和 roster/battle 不一致继续安全拒绝。

### P5：转职 UI 与表现

菜单前必须按 `0487h` 复现妮雅单段、队友请求加妮雅回应两套逐字对话；随后覆盖层以原版职业棋子图像作为四候选视觉主体，同时展示候选顺序、前后数值、职业行动方向、经验归零和生命不恢复。转职结果更新地图棋子；弓兵/修女的额外动作只声明能力，不显示未授权入口。

### P6：验证

增加职业目录一致性、资格、队列顺序、原子提交、最终一击时序、存档迁移和 DOM 输入测试。运行 `pnpm test`、`pnpm build`、`pnpm test:e2e`、逆向基线校验，并人工查看代表性转职截图。

## 退出条件

- 两名具名角色的第 0 关转职路径均可从普通入口真实触发；
- 妮雅与其他队友的两套原版菜单前对话保持正确肖像、上下窗口顺序、原文与自动衔接；
- 四个士兵候选显示各自的原版我方职业图像，像素缩放、透明边缘、2×2 焦点移动与辅助技术标签正确；
- 四个士兵候选均能提交并正确重建零经验属性；
- 当前生命、已行动状态和 PRNG 不因菜单浏览或提交发生额外变化；
- v2/v3/v4 旧档与 v5 新档通过迁移/拒绝矩阵；
- 第 0 关既有无转职流程零回归；
- 代码、内容和 UI 中没有第 1 关部署实现或可玩入口。
