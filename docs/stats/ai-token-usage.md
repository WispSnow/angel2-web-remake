## 1. 口径与字段说明

| 字段 | 来源 | 含义 |
| --- | --- | --- |
| `input_tokens` | API | 本次"新"送入的输入 token(不含 cache 命中) |
| `cache_creation_input_tokens` | API | 本次新写入 prompt cache 的 token |
| `cache_read_input_tokens` | API | 本次从 prompt cache 命中读取的 token |
| `output_tokens` | API | 本次模型回复产生的 token |
| `cached_input_tokens` (Codex) | API | 已包含在 `input_tokens` 中,只计命中比例 |
| `reasoning_output_tokens` (Codex) | API | 已包含在 `output_tokens` 中,只计内部推理占比 |

为避免把 cache 命中当成"工作量",本文同时给出两种口径:

- **total (含 cache 命中)** = API 报回的累计总数,直接相加
- **净消耗** = 真正"新送进去 + 写 cache + 输出"的 token
  - AI Agent A: `input + cache_creation + output`
  - AI Agent B: `(input - cached_input + cache_write) + output`

> 注:不同 Agent 的 `total_tokens` 字段定义略有差异(Agent A 报回 input+cache_creation+cache_read+output;Agent B 报回 input+output),本表已各自相加,不再二次换算。

## 7. 关键观察

1. **净消耗层面 Agent B 多了 2.5 倍**。含 cache 命中时两 AI 几乎打平(50.6% vs 49.4%),但去掉 cache 命中后 Agent B 用了 2.52 亿 token,Agent A 只用了 1 亿。说明 Agent B 每次送入的"新"上下文(代码 / 取证 / 文档)显著更多;Agent A 高度依赖 prompt cache 复用。
2. **Cache 命中率两边都 > 96%**。Agent A: 6.34B cache_read / 6.44B total ≈ 98.4%。Agent B: 6.04B cached / 6.27B total ≈ 96.3%。但 Agent A 的 cache 几乎全部是命中同一份 70-80MB 的工程上下文,Agent B 的 cache 命中跨多个独立 session(每个 session 都会重读关卡脚本 + 原版资源)。
3. **Output 体量反过来 Agent A 多 51%**。Agent A 输出 19.8M,Agent B 输出 13.1M(含 3.4M reasoning)。Agent A 倾向单回合写大块代码/重构;Agent B 倾向多回合短输出 + 内部推理。
4. **时间接力明显**。07-13 → 07-27 全是 Agent B 在做底层取证 + 关卡脚手架;Agent A 08-01 加入后,16-19 日单日 token 量级到 9-10 亿(cache 命中堆得很快),接管了大量代码审阅/精修。

## 10. 已知限制

- 跨电脑合并目前是手工登记(老电脑的 3 个 session 无法被本机 glob 命中,因为路径大小写不同);如未来再有跨电脑迁移,需要在新数据落地后追加此节。
- 部分 Agent A session 的 `cache_read_input_tokens` 累计远大于其它字段之和,可能是 prompt cache 跨多次 long-running session 反复命中,口径定义无误,但绝对值会随单个 session 长度放大。
- `total_tokens` 字段是 API 报回的最终值,在极少数并发场景下与"逐事件累加"有 1‰ 级误差,本文以"逐事件累加"为准。
