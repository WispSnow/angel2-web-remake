# 移动、地形槽与 `MAP.SWF` 原生规则

日期：2026-07-14

## 结论

本轮纠正了早期对 `MAP.SWF` 的两项误判：

1. 第一张表是移动规则 profile；第二张表不是移动代价，而是地形防御百分比。
2. 文件物理上每张表保存 24 个 `u16`，但运行时 profile 的步长只有 `0x2E = 46` 字节，即 **23 个逻辑地形槽**。第 24 个序列化 word 是紧跟 profile 的重叠字，不是第 24 种地形。

因此原版复刻应把每条记录建模为：

```text
movementRules[23]
movementOverlapWord       // 原样保留，不作为地形
terrainDefensePercents[23]
terrainDefenseOverlapWord // 原样保留，不作为地形
```

机器可读结果位于 `reverse/parsed/native/map-rules.json`；底层无损窗口仍保存在 `reverse/parsed/tables/MAP.json` 和 `MAP.csv`。

## 物理文件与运行时重叠布局（C）

`MAP.SWF` 长 3,744 字节，读写器 `0000:1BCE/1C0E/1C45/1C4B` 的确执行：

```text
39 records × 2 windows × 24 words × 2 bytes = 3,744 bytes
```

但两张 profile 指针表说明逻辑结构不同：

- 移动 profile 表：DS:`1F1C`，39 个 `(短码, 指针)` 对。
- 地形防御 profile 表：DS:`26BA`，39 个 `(短码, 指针)` 对。
- 两表内相邻 profile 指针均严格相差 `0x2E`，即 `23 × u16`。

序列化器从每个 profile 指针连续复制 24 个 word，所以第 24 个 word 会落入下一个运行时对象。最直接的边界证据是记录 38“手”的移动窗口末字：

```text
MAP record 38 movement word 23 = 0x4130
DS:26BA                         = 0x4130 = ASCII "0A"
```

它正是第二张 profile 指针表的第一个职业短码，不可能是合理的移动值。这个交叉点把“23 个逻辑槽 + 1 个重叠字”提升为 C，而不是依据值域做出的猜测。原版装载/保存依赖该重叠布局，故修改器与复刻导入器都必须保留物理 24-word 窗口，但玩法只能消费前 23 项。

## 棋盘地形编号链（C）

棋盘的第三张 `50×50` 字节图已可命名为**原始地形 token 图**：

- DS:`01A7` 指向 2,500 个地形 token，现存 44 个场景合计使用了完整的 `0..127`。
- 同一个 token 直接选择配对偶数 `B` 记录中的同号 `40×44` 图块；`0000:47EA` 计算 `token×220` 的位平面源偏移。
- 奇数 `B` 模板首 256 字节是 128 个 `u16` 地形描述偏移，模块 29 保存/恢复到 DS:`2E7D`。
- `0000:4D65` 把 `UN.SWF` 记录 56 解成两张 2,200 字节页。`1000:3EC6` 与 `0000:946A` 以 token 查 DS:`2E7D`，再用得到的偏移查第一页，得到逻辑槽号。
- 逻辑槽号乘 2 后分别查询 DS:`1F1C` 或 DS:`26BA` 所选 profile。

这条链已对 44 个场景逐项验证：共 36 张不同描述表，128 个 token 均解析成功，所有偏移均落在第一页边界内，所有结果均落在 23 个逻辑槽内。现存模板实际使用槽 `0..16,18..21`；槽 17、22 没有配置引用。机器表位于 `reverse/parsed/native/terrain-token-map.json`。

对“逻辑槽是否存在原版可见名称”的调用链审计现也已完成。Ghidra 对 DS:`2E7D` 报告的六个读取点已逐一验证：`28B9h` 用于小地图颜色，`9476h/9F5Ah` 用于地形防御，`963Eh` 用于攻击表现选择，`1000:3ECBh` 用于移动规则，`1000:3EE6h` 返回逻辑槽给地形改变/判定路径；没有一个进入字形、字符串或 HUD 名称绘制器。因此当前不能再预设“原作一定有一张 23 项显示名表”。逻辑槽的规范标识保持 `0..22`。

`A/0007` 的 415 字形图集中确有草、树、坡、壁、山、桥、浅、海、泽、深、礁、城、墙、磁、阶、梯、王座、红布、屋、木板、井、杉、栏、牌、花等地形/场景词汇，但字形数组没有字符串分隔符或槽索引。这些词只可作为未来编辑器中的视觉分类候选，不能据相邻顺序、瓦片外观或小地图颜色绑定到逻辑槽。机器审计见 `reverse/parsed/native/terrain-name-audit.json`。

第二张 2,200 字节页的用途现也已闭合：`0000:285D/2884` 扫描 50 行×50 列，屏幕起点为 `(485,161)`，横纵均每格递增 3 像素；`0000:28A4` 对 token 0 不绘制，对其他 token 通过第二页取得 `0..15` VGA 调色板索引，填入宽 3、高 3、颜色字段后调用 `0000:D050` 实心矩形绘制器。因此该页应命名为**地形小地图颜色页**，不是第二套玩法属性。44 张 150×150 的地形小地图已输出到 `reverse/renders/battle-maps/minimap/`。

完整叠加层同样已闭合。战斗模块 29 的 `28DDh/2924h` 扫描阵营/占用图：值 1、2、`FFh` 都先画调色板 0 的 `4×4` 外框，再在 `(x+1,y+1)` 画 `2×2` 内芯，颜色依次为 10、11、15；`FFh` 目前只能命名为“白色占用标记”。44 个模板的值域严格为 `0/1/2/255`，计数分别为 108,905/137/535/423，并已生成 44 张叠加图到 `reverse/renders/battle-maps/minimap-occupancy/`。

部署模块 27 不直接复用这套 3 像素地形／颜色 10 的战术小地图。`165Bh..17EEh` 在
`(440,125)` 另画固定 `50×50`、每格 `4×4` 的 `200×200` 全图；side 1／side 2／`FFh`
的 `2×2` 内芯依次使用颜色 9／11／15，当前 `FFh` 则以颜色 15 外格＋颜色 0 内芯与普通
黑外格＋白内芯反相。部署专用结构见 `input-and-battle-ui.md` 与 `input-ui.json` v6。

当前战场视口由 DS:`5390/5392` 给出左上格，映射到小地图后用黑色四边框表示；横边 `29×1`、竖边 `1×20`，整体覆盖 `30×21` 像素，对应 `10×7` 格。鼠标位于小地图内时另画同尺寸白框作为预览；主键点击以预览原点 `+4,+3` 作为焦点，再按战场边界重新夹取视口。五个 `WAR` 首四个 word 已据此命名为视口原点 X/Y 与战场光标/焦点 X/Y，并输出五张真实存档态小地图到 `reverse/renders/battle-maps/save-minimap/`。完整常量、17 段代码签名和三组矩形数据签名见 `reverse/parsed/native/minimap-rules.json`。

## 第二张 profile：地形防御百分比（C）

`0000:946A → 1000:41A1` 明确使用 DS:`26BA` 的第二张 profile。普通攻击准备链随后执行：

```text
terrainDefense = floor(effectiveDefense * terrainDefensePercent / 100)
```

普通记录 0–34 的前 23 个逻辑值域为：

```text
1, 5, 10, 15, 20, 25, 30, 40, 50, 99
```

所以第二张表的 5–50 并不是移动点消耗。`99` 同样按百分数参与地形防御公式；在可见地形名未绑定前，不应擅自改成“无效值”。

## 第一张 profile：移动规则（C）

`1000:3EC6 → 1000:4186` 使用 DS:`1F1C` 的第一张 profile。已有两个独立移动消费者：

- 玩家/通用落点校验 `1000:690B` 查询目标地形规则，值为 `99` 时立即拒绝；随后还要求临时路径图比较通过、目标阵营图为空。
- AI 邻格试移 `0000:939E` 要求目标为空，并同时拒绝 `99` 与 `98`。

普通记录的逻辑值域严格是：

```text
1, 2, 3, 4, 5, 98, 99
```

传播回调现已静态定位，所以第一张表及 `1..5` 的含义都可提升为 C：它们是加权模式进入目标格时扣除的地形移动代价。当前能写进原版行为的边界是：

- `99`：玩家落点与 AI 邻格试移均不可用（C）。
- `98`：普通玩家移动模式 `M` 在传播阶段明确拒绝，AI 邻格试移也拒绝；因此后置落点函数只显式拒绝 `99` 并不表示 `98` 可达（C）。
- `1..5`：从当前剩余范围扣除的目标地形代价（C）。

所有当前 profile 中实际含 `98` 的职业都走普通 `M` 模式；唯一的玩家移动模式例外是记录 26 `0N/水戰士`，但它自己的 profile 没有 `98`。所以仍不能把 `98` 擅自命名为“水路”或某种具体地形；能确认的是它在普通玩家移动中不可传播，而 `F*` 等非移动业务模式会采用不同过滤规则。

## 可达范围生成与精确递推（C）

玩家移动入口 `0000:7310` 读取当前单位的移动属性，写入范围参数后调用 `1000:39D4`。此前把传播回调视为“战斗时装入”的原因是 Ghidra 的平坦合成地址没有保留 Borland 内部代码段基址。实际换算为：

```text
当前代码段线性基址       = 139D0h
DS:1F0B 保存的近调用偏移 = 01CDh
139D0h + 01CDh           = 13B9Dh = 六模式传播分发器
```

所以回调完整存在于静态解包镜像，无需等待运行时覆盖。范围生成器：

1. 清零一张 2,500 字节临时图。
2. 在起点写入传入的移动值。
3. 以 `±1`、`±50` 四个正交邻居传播。
4. 每轮分别正向和反向扫描整张 `50×50` 图，直到没有新变化。
5. 对每条边计算 `candidate = currentRemaining - stepCost`；无符号下溢、结果为 0 或不大于目标格旧值时不更新。
6. 落点时再检查第一张 profile、临时图非零和占格。

临时图的数值语义是“含当前格在内的剩余范围”。起点写入移动属性，因每次更新要求候选严格大于 0，所以一条路径可达当且仅当累计进入代价严格小于移动值；全为代价 1 时最大步数是 `movement - 1`。

玩家「移動」命令 `0000:7310` 有两种已确认分支，由 `0000:7336` 按职业码选择；seed 一律取该单位的移动力 `DS:31C5h`：

| 职业 | 模式 | 传播规则 | 占格规则 |
| --- | --- | --- | --- |
| 除 `0N` 外的玩家职业 | `M` | 进入目标格扣其 `1..5`；拒绝 `98/99` | 可穿过空格或 side 1 友军格，不穿过敌军格 |
| `0N/水戰士` | `0` | 所有非 `99` 地形统一扣 1 | 传播时不读取阵营图 |

`1N/半龍戰士` 的「技術」命令 `0000:7475` 复用同一套落点校验与移動表现，但用固定 seed `200` 和模式 `0`，因此覆盖全图；它不是「移動」分支，规则详见 `shooting-and-technique-system.md` 的“职业直连技術”。

无论传播模式如何，最终落点仍必须在临时图中非零、地形规则不为 `99`，并且阵营/占用图为空。因此水戰士与半龍戰士“传播时可越过占格”不等于可以停在已占格上。

同一通用生成器还包含以下模式；本轮已把 AI 主调用者和 `C*` 伤害阵营过滤绑定到具体业务：

| 模式码 | 代价 | 拒绝规则值 | 占格过滤 | 已确认业务 |
| --- | --- | --- | --- | --- |
| `0` | 1 | `99` | 无 | 水戰士移动、AI 水戰士覆写、`1N/半龍戰士` 技術（`0000:748B`，seed `200`）及通用效果图 |
| `1` | 地形值 | `99` | 无 | 43 个模式生产点穷举后确认没有调用者；保留的不可达/遗留分支 |
| `2` | 1 | `0/99` | 无 | 玩家与 AI 射击范围 |
| `M/Y/A` | 地形值 | `98/99` | 空格或所选阵营；`M/A→1`、`Y→2` | 玩家移动/构造；side 2 AI 基础移动；side 1 自动 AI 基础移动 |
| `FM/FY/FA` | 1 | `99` | 空格或所选阵营；`FM/FA→1`、`FY→2` | `FY/FA` 为对应 AI 阵营的远距追逐图；`FM` 为场景 `0/1/6/20/21/22/42` 的剧情脚本移动 |

`1000:14D8/1519` 分别把 side 2/side 1 的基础、远距模式设为 `Y/FY` 与 `A/FA`。`1000:4264` 按目标阵营选择 `CM/CY`，`0000:644D` 再据此跳过异阵营的一点击伤。完整 AI 调用链见 `ai-decision-system.md`。

对 DS:`1F0Fh` 的全模块生产者审计找到 43 处写入：27 处立即数和 16 处 `AX`。立即数集合只有 `0/2/M/A/FM`；16 个动态写入中一个明确写 0，12 个来自只可能为 `0/Y/A` 的 CS:`017Fh`，三个来自只可能为 `FY/FA` 的 CS:`0181h`。不存在 ASCII `1` 的生产者，所以 `1000:3BE0h` 虽有完整算法，却在发布模块中不可达。十处 `FM` 立即数则全部位于场景 `0/1/6/20/21/22/42` 处理器；它统一扣 1、拒绝 99，可穿过空格或 side 1 单位，正是已闭合逐格剧情移动的范围图。机器化的偏移清单、上游值域和断言见 `../parsed/native/map-rules.json` 的 `producerAudit`。

## 敌方邻格的 `FFh` 保留与转换（C）

复核：2026-08-17；此前把这层标记记为「`Y/A/FY/FA` 的 AI 目标标记」，实测扫描分支后确认
**模式 `M` 同样执行前两步**，因此它不是 AI 专属，而是双方共用的「控制区」实现。三步拆开：

| 步骤 | 入口 | 适用模式 | 行为 |
| --- | --- | --- | --- |
| 保留 | `1000:3D6D → 3E12 → 3E3B` | `M/A/Y/FM/FA/FY/CM/CY` | 敌方单位的四个正交邻格中，**阵营图字节为 0**（空格）且移动规则非 `98/99` 者写 `FFh`；传播因此无法穿过 |
| 转换 | `1000:3DC5 → 3E12 → 3E81` | 同上 | 保留格若某个正交邻格的原始剩余值**大于 1**（且该邻格不是 `FFh`）则写 1，否则清 0 |
| 收尾 | `1000:40EE → 412F/413D` | 仅 `Y/A/FY/FA` | 全部非零格加一；再把四邻存在大于 1 的**敌方占格**写成 1 |

两条容易被漏掉的原版事实：

1. **占格不被保留。** `1000:3E3B` 先读阵营图，只有空格进保留集合。同阵营单位所在格因此
   仍是普通格，而 `M/A/Y` 的传播允许穿过同阵营格，所以原版可以从站在敌人旁边的友军身上
   穿过去并继续前进——友军等于在控制区上开了一个可通行的缺口（但仍不能停在它上面）。
2. **转换判据不看该格自己的地形代价。** 判据只有「邻格剩余 ≥ 2」（`1000:3E8E` 的
   `cmp al,1 / ja`），全程没有 `剩余 − 该格代价` 这一步；代价值只在保留阶段用于排除
   `98/99`。因为正常更新是 `candidate = 剩余 − 代价 > 0`，「剩余 ≥ 2」恰好是**代价为 1**
   时「还能再走一步」的条件，所以这是按代价 1 写死最后一步的实现疏漏：代价 1 地形上两种
   算法逐格等价，代价 `s ≥ 2` 时原版多给 `s − 1` 点，代价 5 最多多给 4 点。

因此最终图的语义仍是：攻击邻格为 2、可攻击的敌军格为 1、其余可达格为传播剩余值加一；
近战落点与远距追逐依赖这组标记，详细选位见 `ai-decision-system.md`。复刻对这两点的处理
方向相反——第 1 点属于要贴合的原版行为，已由 `../gdd/web-remake-rule-decisions.md` 的
`REMAKE-105` 补回 `src/game/simulation/grid.ts`；第 2 点由同一文件的 `REMAKE-104` 明确
决定不复现（贴身最后一步照常按地形代价结算）。

第 1 点在复刻里另有一处不影响结论的实现差异需要记录：`1000:3E3B` 的保留条件是「阵营图
为 0 **且**移动规则非 `98/99`」，复刻只实现了前半条。后半条在复刻中不可观测——传播本身
就拒绝进入 `98/99` 格，把这些格记进保留集合不会改变任何一条通路。若将来出现能落在
`98/99` 格上的模式，这半条必须一并补上。

后续取证重点缩小为：

- 模式 `1` 只在底层兼容规格保留精确算法，不作为原版可见动作；`FM` 已无未绑定生产者；
- 仅在发现新的原生 UI/字符串绑定时才给逻辑槽增加原版名称；当前六个描述表消费者已穷尽且没有名称路径；
- 对水戰士可越过占格这一原版行为做实机表现确认，但不再以实机结果决定公式。

## 走路表现与「移動」音效门（C）

日期：2026-08-17

此前只把 `E/14` 绑定为逐关脚本移动的声音（`stage-event-presentations.md`），
四个音效开关中「移動」（`DS:10EC`）的消费者也一直没有登记。本轮把两者一并闭合：
**`E/14` 是所有棋盘移动共用的走路声，不是脚本移动专属。**

`DS:10EC` 在整个模块 29 只有一个读取点，即门控 VOC 包装器 `0000:0249`
（`test byte [10ECh],1` 命中后进入 `0000:0254` 的公共提交），与已闭合的
`0224`（戰鬥）、`0233`（按鍵）、`023E`（說話）并列。`0249` 在全模块也只有一个
调用者：共用走路播放器 `1000:7F72`。

```text
1000:7F22 / 1000:7F4A   两个等价远调用外壳，各自把 DS:6004、DS:FA7A 置 'N' 后
                        near-call 同一个 1000:7F72
1000:7F72               cmp byte [77AF],'N' → 命中则 jmp 1000:805B 静默返回
1000:7F7C..7F92         BX=3、CX=0Eh 载入 E/14
1000:7F9A               callf 0000:0249  ← 经「移動」开关提交，异步播放
```

`DS:77AF` 由建路函数 `1000:7E09` 写入：`cmp si,di` 相等（起点==终点）时写 `'N'`
并直接返回，否则建立前驱链后写 `'Y'`。因此**零步移动既不走动画也不发声**，
而任何实际位移都在第一格之前一次性提交 `E/14`（5000 Hz 单声道 1.261 秒），
不是逐格重播。

进入 `7F72` 的五条业务路径已穷举：

| 业务 | 调用点 | 外壳 |
| --- | --- | --- |
| 玩家 `移動` 命令 `0000:7310` | `0000:738F` 建路、`0000:7394` 播放 | `7E09`/`7F22` |
| `1N/半龍戰士` 直连技術 `0000:7475` | `0000:74DF`/`0000:74E4` | `7E09`/`7F22` |
| 工兵構築 `1K/2K` 的 `772Dh` | `0000:7770`/`0000:7775` | `7E09`/`7F22` |
| side 1 自动与 side 2 AI 移动 | `1000:1B1D..2202` 十对 | `7E09`/`7F4A` |
| 逐关脚本移动 `1000:7DF7` | 13 处处理器调用 | `7E09`/`7F4A` |

聚焦原语 `1000:830B/830F` 虽然也调用建路函数，但随后把 `DS:77AF` 直接写 `'N'`，
所以镜头缓动不发声，与 `stage-event-presentations.md` 的既有结论一致。

取消移动没有独立的反向走路：`0000:693B/6A55/6B6A` 等路径直接恢复棋盘格并清高位
（见 `turn-action-system.md`），因此原版不存在「返悔走路声」这一事项。Web 复刻
如果为可读性补上反向走路演出，是否配音属于 `[DD]`。

### 复算命令

```sh
python3 - <<'PY'
data = open('reverse/unpacked/lzexe-modules/raw/0029-unpacked.bin', 'rb').read()
# DS:10EC 的唯一 bit-0 读取点
print([hex(o) for o in range(len(data) - 5)
       if data[o:o + 5] == bytes([0xF6, 0x06, 0xEC, 0x10, 0x01])])
# 远调用按线性地址匹配：seg16*16+off16 == 0x0249
print([hex(o) for o in range(len(data) - 5) if data[o] == 0x9A
       and (int.from_bytes(data[o + 3:o + 5], 'little') << 4)
           + int.from_bytes(data[o + 1:o + 3], 'little') == 0x0249])
PY
```

预期分别输出 `['0x249']` 与 `['0x17f9a']`（即 `1000:7F9A`）。段字是任意 seg:off
拆分（这里是 `0000:0249`，别处如 `17DE:0142`），必须按线性地址比对，不能按固定
段常量搜索。
