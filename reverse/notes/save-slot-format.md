# `WAR*.TST` / `JUST.TST` 存档状态格式

日期：2026-07-15

## 结论

模块 29 的读写两端已经闭环，六个 `.TST` 均可无损解码：

- `WAR0.TST` 至 `WAR4.TST` 是五个编号战中存档槽，每个解为 11,972 字节。
- `JUST.TST` 是模块 27 为下一场重新生成、并在 GO 共享字段 `CONTINU='N'` 时由模块 29 载入的战斗状态模板，解为 8,358 字节。
- 文件主体使用 16 字节循环 XOR 和简单 RLE，不是覆盖代码；文件头偶然呈现的 8086 指令字节只是 XOR key。
- 导出器已输出解码二进制、分段布局和活动单位实例，位置见 `reverse/extracted/saves/decoded/` 与 `reverse/parsed/saves/TST-decoded.json`。

## 文件头、XOR 与 RLE

文件偏移 `00h` 的 little-endian `u16` 是压缩流的绝对结束偏移。压缩流从 `32h` 开始，因此有效加密载荷为 `[32h, firstWord)`。保存器用 `firstWord + 12h` 作为 DOS 写文件长度，所以所有六个样本都满足：

```text
firstWord == fileSize - 18
```

偏移 `02h..11h` 的 16 字节为循环 XOR key。读端从 `32h` 开始依次异或，key 用尽后回到 `02h`。保存器只覆写前 15 字节；第 16 字节是复用文件缓冲区的原值，并非固定零：`JUST/WAR0..4` 的发布样本依次是 `02/00/00/55/A8/00h`。

这 15 字节也不是战斗随机数。模块 27 `0000:122Eh` 与模块 29 `1000:8B3Eh` 都以游标顺序读取代码段 `0101h..0700h`；越界分支把游标复位为 `0100h` 却不写 `AL`，所以复位当次甚至会沿用调用者留下的 `AL`。两函数均不读取 PIT `40h` 或其他熵源。它只是混淆用的代码字节/残留缓冲组合，不是安全加密，也不携带可重放的随机种子。

解密后的 RLE 规则：

- `< C0h`：字面量，直接输出。
- `C0h..FFh`：低六位是重复次数，下一字节是重复值。
- 保存器用 `C1h,value` 转义原值 `>= C0h` 的单个字节。

写端为 `ANGEL2_RLE_COMPRESS_SAVE_BUFFER`（`1000:8AA2`）与 `ANGEL2_OBFUSCATE_SAVE_BUFFER`（`1000:8A54`）；`WAR` 读端为 `1000:108F/10C1`，`JUST` 读端为 `1000:560B/563D`。六样本的完整声明压缩流均可严格解码；五个 `WAR` 全部展开为 11,972 字节。

原生读端另有两项不影响有效样本玩法状态、但兼容层必须知道的边界错误：

- 首字实际是压缩流的绝对结束偏移，但 XOR 例程却把它直接当成“从 `32h` 起的字节数”。所以读写两端都会多异或 50 字节；写端只把其中 18 字节落盘，读端还会访问 EOF 后 32 字节的工作缓冲。
- `WAR` RLE 循环目标是 `237Ch + 05A0h + 05A0h = 11,964`，不是写端完整原始长度 11,972。五样本最后一个游程分别把输出推进到 11,967/11,967/11,966/11,966/11,966 后停止，并留下 5/5/7/7/7 个声明压缩字节未读。差异全部位于解压偏移 11,716 后的 256 字节无消费者填充；十四段恢复调用仍取得完全相同的玩法状态。`JUST` 的目标 8,358 则与完整流精确一致。

保存器在压缩流结束后仍额外写 18 字节缓冲尾部；读端按目标解压长度停止，不把它当作独立结构。因此这 18 字节不是已确认的校验、指针表或覆盖代码，只能作为发布版写器指纹。安全导入器可以忽略 `firstWord` 后任意长度的尾随字节；导出原生格式时才复现 `+18` 约定。

## 槽位列表元数据

模块 23 的槽位扫描器把 `WAR0.TST` 的数字从 0 循环到 4，每个文件只预读前 50 字节。打开失败时，对应五个 UI 数组写入 `5858h`（原始字节 `XX`）。扫描器从 `12h/14h/16h/18h/1Eh` 读取五个 `u16`。模块 23 与模块 29 都内嵌同一行 Big5 表头：`職業/等級/經驗值/儲存次數/難度`，所以五列正式名称已经闭合。

保存器实际从 `12h` 起写七个 word：

| 文件偏移 | 原生来源 | 当前语义 |
| ---: | --- | --- |
| `12h` | DS:`319Dh` | `職業`；两字节 ASCII 职业码，经原生描述符表显示职业名 |
| `14h` | DS:`31BDh` | `等級`；当前工作单位的成长/等级行 |
| `16h` | DS:`318Eh` | `經驗值`；保存前刷新为 side 1 槽 0 的累计经验 |
| `18h` | DS:`00BCh` 加一后写回 | `儲存次數`；GO 原符号 `SAVE_NUM`，先累计再写入 |
| `1Ah` | DS:`2E77h` | 场景/关卡编号 |
| `1Ch` | DS:`2F83h`；999 保存为 1000 | 回合/战斗结果状态；999 是即时胜利，1000 是已保存胜利 |
| `1Eh` | DS:`0000h` | GO 原符号 `LV_HARD`；0“過關斬將”、1“勢均力敵”、2“困難重重”、3“無法無天” |

`1Ch` 的胜利边界已经由模块 29 主循环闭合：运行中胜利写 999，`1000:88B9` 仅在构造文件元数据时把它改写为 1000；载入 1000 会执行必要的战后分发，但跳过再次询问保存。`1Eh` 已通过 GO 状态块导出关系、模块 23 的四项选择菜单/槽位标签表，以及模块 29 的场景 30/敌方属性消费者绑定为 `LV_HARD`；值 0–3 分别选择 8/16/24/32 个场景 30 职业形态，值 3 另给 side 2 攻防与最大生命加半。

保存端有一项应保留的原版细节。`1000:8882` 先用 `side=1, slot=0` 调用 `0000:5083`；该链会刷新 DS:`318Eh` 的累计经验，却不会调用 `0000:51ECh` 重新解析职业描述符和等级行。因此 `職業/等級` 是进入保存器前已有工作单位的快照，`經驗值` 则固定来自 side 1 槽 0，两者在极端情况下可能不属于同一单位。这不是字段未解，而是发布版写端的真实不一致；严格兼容模式应保留，改良模式才可明确修正。

| `WAR0.TST` | 士兵 | 1 | 78 | 6 | 無法無天 |
| `WAR1.TST` | 魔術士 | 1 | 78 | 7 | 無法無天 |

### 双方 60×24 字节单位动态状态

DS:`45D0h/4BECh` 各有 60 个 `u16` 指针，逐项严格等于对应基址加 `slot×24`；两侧长度字均为 1,440。side 2 槽 54 指向 DS:`5176h`，与场景 37 头部单位状态的独立证据吻合。虽然职业数组有 75 槽，发布版单位动态记录容量是每侧 60 槽；五个现存 `WAR` 的活动槽最大为 48，全部模板最大为 58，均未越界。

每条记录布局：

| 记录偏移 | 含义 |
| ---: | --- |
| `00h` | 当前生命 |
| `02h` | 累计经验 |
| `04h` | 未命名兼容字；当前单位装载器跳过，全部 DS:`31B9h` 当前状态指针消费者也不读取 |
| `06h` | 未命名兼容字；复制到 DS:`31A5h`，但没有读取其值的规则消费者；已知访问均从该地址再加 `08h..16h`，实际读取后续八状态 |
| `08h/0Ah/0Ch/0Eh` | 攻击提升、防御提升、防魔、混乱 |
| `10h/12h/14h/16h` | 攻击下降、防御下降、中毒、禁咒 |

八个状态字均以 bit 15 表示有效、低 15 位表示剩余回合。双方原生初值和五个 `WAR` 的十份块中，`04h` 都是同一组 60 字初值，`06h` 的 600 个样本字全为 0；`1000:35F2h` 的整阵营状态 tick 只遍历 `08h..16h`。因此两字的行为边界已经闭合：兼容层必须原样往返，但不得赋予游戏效果；只有原源代码名称不可恢复。机器审计见 `../parsed/native/save-state-semantics.json`。

## `JUST.TST`

上层 `0000:4BD9` 在共享字段 `CONTINU` 不是 `N` 时进入编号 `WAR` 载入器；值为 `N` 时调用 `1000:5386` 打开 `JUST.TST`。模块 23 已确认新游戏写 `CONTINU='N'`，继续游戏则写 ASCII `0..4`；更上游的模块 27 `0000:0FF8` 会创建/截断 `JUST.TST`，将当前场景的 `B.SWF` 模板与战役单位职业合并，再用同一组 RLE/XOR 函数写出。

解压后的固定顺序为：单位槽图 2,500 字节、阵营/占用图 2,500 字节、side 2 职业 150 字节、合并后 side 1 职业 150 字节、side 2 逐槽 AI 行为 150 字节、场景号 2 字节、原始地形 token 图 2,500 字节、128 个 `u16` 地形描述偏移 256 字节、side 1 逐槽 AI 行为 150 字节，总计 8,358 字节。描述表位于偏移 7,952，由模块 29 `1000:55DBh` 恢复到 DS:`2E7D`。

模块 27 会把未填满的玩家部署格以阵营值 `FFh` 原样序列化进 `JUST`；模块 29 `1000:543B` 在正式开战前把残余 `FFh` 统一清成 0。因此 `FFh` 是部署阶段状态，不是第三阵营，也不会留在正式战斗棋盘。名单、固定单位、部署格和开战流程见 `battle-lifecycle.md`。

它不是第六个用户存档槽，而是可被每关重新生成的“下一场战斗状态”。仓库中当前样本的场景号为 0，所以它恰好表示第一战；这不是文件格式的唯一用途。完整上游格式见 `battle-template-format.md`。

### 参考样本哈希审计（2026-08-03）

一次原版试玩误把 `ref/ANGEL2` 当成了可写目录，导致 `JUST.TST` 与 `WAR0.TST` 的原始文件哈希漂移。两者不能用同一方式处理：

- `JUST.TST` 从 `f69a2838...` 变为 `c358370c...`，但两份文件解压后均为完全相同的 8,358 字节，解压状态 SHA-256 都是 `1c34c1f06a87ebdffbca404d0ed7be8c0df8b7674e573eec19f7409367eecfc5`。差异仅位于不承载玩法语义的 XOR key 和写器尾部，所以参考清单接受后者作为当前规范原始编码。
- `WAR0.TST` 的漂移版本 `84de1bf0...` 解压后有 1,385 个字节与登记样本不同，活动单位数也从 15 变为 6；这是一次真实的后续存档，不是等价编码。该版本不能替换证据基线，参考目录已恢复为原登记哈希 `30b4c5f9...`。

此审计不改变格式结论、Web 运行时内容或任何玩法规则；它只区分“等价混淆编码”和“不同玩法快照”。原版实机仍必须只挂载 `reverse/work/ANGEL2`。

## 损坏、版本与安全导入边界

发布格式没有 magic、版本字段、校验和、认证长度或旧版迁移分支。可识别的只有角色相关的完整展开长度，以及发布写器的 `fileSize == firstWord + 18` 指纹；因此不存在可由某个头字段回答的“旧版本兼容”。来源不明的文件只能按结构和布局指纹识别。

原版也没有可复用的容错策略：

- 模块 23 `3CE2h` 只检查打开文件的 carry；打开失败才把槽位显示成 `XX`。50 字节读取是否失败、实际读了多少字节均不检查，随后仍从目标缓冲读五项元数据。
- `WAR` 载入器 `1000:0DD0h` 先以 `0002h` 填满 64 KiB 工作区，再对打开、最多 65,535 字节读取和关闭全部不检查返回值；之后无条件解密、解压并恢复十四段状态。
- `JUST` 载入器 `1000:5386h` 同样不检查打开、读取或关闭。两套 RLE 都没有源结束、`C0h` 零游程、目标精确长度或末游程越界检查。
- `WAR/JUST` 写器对创建/截断、写入长度和关闭也都不检查；磁盘错误可能留下一个看似存在但截断的文件。

所以损坏输入的“原版行为”是使用旧缓冲、读越界或写过目标等未定义内存行为，不是降级恢复。Web 版不能为了兼容去模拟内存破坏。安全导入分三层：

1. 结构硬拒绝：文件少于 50 字节；`firstWord` 不在 `[32h,fileSize]`；游程缺值；`C0h` 零游程；完整声明流不能无越界地精确展开为 `WAR=11,972` 或 `JUST=8,358`。
2. 语义校验：会形成数组越界/不存在单位状态记录的值拒绝进入模拟；安全但异常的关卡、难度或保留字段只警告并原样保留，不静默“修复”，以免破坏 Mod。
3. Web 原生扩展：在 legacy payload 外层增加 `schemaVersion`、内容/Mod 哈希、载荷长度与校验和；不得伪造到原生 `.TST` 未使用的头部字节中。

尾随字节不参与原生解码边界，因此安全导入可接受缺少 18 字节尾部或有更多尾随数据，同时把“恰为 18”单独记录为发布写器指纹。12 项合成损坏语料、六样本语义检查和 21 段代码签名见 `../parsed/native/save-robustness.json`。

## 随机状态与确定性重放

`.TST` 是玩法快照，不是确定性重放点。`WAR` 没有保存 RNG seed、PIT 相位/计数器或输入事件流；普通伤害 `0000:95D2h` 直接读取 PIT `40h`，AI `1000:2016h`、祈祷 `1000:5BE6h`、踏地 `1000:7460h` 又分别使用不在十四段序列化范围内的 `CS:0BC1h`、DS:`6024h`、`CS:00CBh` 累加状态。射击闪避、AI 暂缓/移动、路径等价邻格与胜利肖像也受 PIT 影响。

因此载入同一 `WAR` 后重复相同玩家选择，伤害、AI 决策、等价路线或纯表现分支都可能不同；“是否保存随机种子”现已确认答案为否。未来 Web 版若要可重放，必须另存确定性 PRNG 算法与状态/调用序号、稳定模拟边界上的语义动作日志、初始快照哈希、规则版本和有序 Mod/内容哈希，并让表现帧率/音频完成时机不能消耗模拟随机数。这是明确的现代扩展，不属于原生 `.TST` 字段。
